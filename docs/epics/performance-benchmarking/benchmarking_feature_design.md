# Feature: Site Benchmarking & Forecasts

## 1. Overview

Benchmarking adds a natural-language insight below the Traffic graph of the Site Kit dashboard ([Benchmarking PRD](https://docs.google.com/document/d/1zwM9ogRlrFO__rLFVYT6SE1qqsjIwzfFUELBiLnYHUQ/edit?tab=t.0)). It tells the site owner whether the last period was normal for the site, what changed, and what carried the change, using the site's own history as the yardstick.

The work is split between two parties:

| Party | Runs | Produces |
| :--- | :--- | :--- |
| **Client**: the WordPress plugin (`site-kit-wp`) in production; the Go code in this repository offline | Report retrieval, period totals, last year's totals for the same windows, the expected range, the chart corridor, contextual rows, landing page classification, the key factor cards | The request to `POST /v1/ai/benchmarking` (§4), including the cards it renders itself |
| **Endpoint**: this service | Validation, sanitization of its copy of the contextual data, trends (range status, distance, the last-year verdict, the change), scenario labelling, prompt construction, the model call, output validation | The narrative (§6): `scenario`, `analysis`, `driver` |

The Go client is the reference implementation of everything in §5. Offline it builds requests from checked-in GA4, Search Console and WordPress exports (`internal/ai/benchmark_dataset.go`), computes the baseline (`internal/ai/baseline_model.go`), classifies pages (`internal/ai/page_classifier.go`) and computes the cards (`internal/ai/key_factors_client.go` over `internal/ai/traffic_decomposition.go`). §5 states the goals and the logic in enough detail to port; where this document and the Go code disagree, the code is right and the document is a bug.

**Two questions, two comparisons.** The insight answers two separate questions, each against its own yardstick, and never mixes them:

| Question | Fields | Compared against | Inputs |
| :--- | :--- | :--- | :--- |
| *Was this period normal for my site?* | `analysis` | the site's long-term expected range for a `d`-day total (§5.4), and the same windows a year earlier (§5.5) | `status_vs_baseline`, `range_distance_pct`, `range_transition`, `repeat_last_year` |
| *What changed, and what carried it?* | `driver`, the key factor cards | the previous `d` days | `current_period_traffic`, `current_period_traffic_pct`, the visit totals, `shape`, `subject`, the cards |

The two answers may point different ways (traffic higher than usual while visits fell against the previous `d` days); each field states its own answer and never reconciles them with period-over-period numbers. The one exception is `range_transition` (§7.4): when the previous period sat outside the expected range, `analysis` uses a fixed transition phrase ("returning to what's normal for your site after an earlier spike/dip", or "though down from its recent peak / up from its recent low") without stating any period-over-period figure or percentage. `d` is the header date range the reader picked (7, 14, 28 or 90 days in the dashboards).

## 2. Narrative Requirements

The text the model writes must be:

- **Concise and non-technical.** Plain words, no jargon or marketing buzzwords, no idioms that do not translate (`level off`, `bounce back`, `hold steady` and similar are banned in every language).
- **Correlative, not causal.** Overlapping movements are reported as coinciding, never as causing one another. The ban covers causal conjunctions (`because`, `due to`, `karena`, `ya que`, `parce que`, `perché`, `weil`) and causative verbs and participles (`causing`, `driving the overall decline`, `resulting in`, `entraînant`, `provoquant`, `causando`, `verursachend`). The one exception is `led by` (and its localized equivalents) for parent-to-child attribution inside a card (*"Organic Search (led by /pricing)"*), which describes composition.
- **Bound to the cards and the data.** The driver names only what the key factor cards and the contextual data contain, quotes each figure with the name it belongs to, and never offers an unmeasured explanation (brand awareness, word of mouth, dark social, bookmarks, algorithm updates).
- **Observational.** No SEO advice or promised visibility outcomes, no suggestion to audit tags or tracking, no doubt cast on the site's own measurement, no instructions on what to publish or fix.
- **Localized.** The `hl` locale decides the language; figures, bolded entity names and channel names are preserved exactly.

### Example outputs

The scenario label is `<status_vs_baseline>.<current_period_traffic>` (§7.5).

The analysis wording rotates between three variants ("usual", "normal", "typical") by the period's end date (§7.6, *Range wording*); the examples below are variant A.
- **Analysis, `ABOVE_EXPECTED` with a distance**: *"Your traffic over the last 28 days is about 18% higher than usual for your site."*
- **Analysis, `ABOVE_EXPECTED` under 1% beyond the range**: *"Your traffic over the last 28 days is slightly higher than usual for your site."*
- **Analysis, `BELOW_EXPECTED` with `repeat_last_year`**: *"Your traffic over the last 28 days is about 11% lower than usual for your site, and traffic also fell at this time last year."*
- **Analysis, `WITHIN_EXPECTED`**: *"Your traffic over the last 28 days is in line with what's usual for your site."*
- **Analysis, `NO_RANGE` with `history_days`**: *"Your traffic over the last 28 days — we're still learning what's usual for your site; check back in about 3 weeks."*
- **Driver, an unchanged total**: *"Visits were the same as the previous 28 days, as **Organic Search** rose 37.5% (+150 visits) while **Direct** fell (-150 visits)."*
- **Driver, `CONCENTRATED`**: *"Visits fell 33.3% (-400 visits) compared to the previous 28 days, led by **Direct**, which fell sharply (-300 visits)."*
- **Driver, `DIFFUSE`**: *"Visits rose 25.0% (+1,500 visits) compared to the previous 28 days, spread across **Direct** (+800 visits) and **Organic Search** (+700 visits)."*
- **Driver, `BELOW_EXPECTED.UP`** (the two questions point different ways): *"Visits rose 15.0% (+1,200 visits) compared to the previous 28 days, led by **Organic Search** (+900 visits) alongside **Referral** (+500 visits), partly offset by **Direct** (-200 visits)."*
- **Driver with a `SEARCH_QUERY` subject**: *"Visits rose 12.0% (+350 visits) compared to the previous 28 days, led by **Organic Search** (+350 visits), with search query "**best running shoes**" up 400 clicks."*

## 3. One Traffic Unit: Visits

Benchmarking counts **visits**: GA4 `sessions`. Every traffic figure the feature computes, compares, shows or narrates is a visit count: the daily series, the expected range, the period totals and last year's totals, every contextual breakdown, every key factor card and sub-row, the ranked impacts and the narrative. One person arriving three times is three visits.

**Why visits.** Visits add up across every dimension the feature breaks traffic down by (channel, device, visitor type, landing page, referrer): every session has exactly one value of each, so the parts sum to the whole. Users do not (one person arriving through Organic Search and later through Direct is one user in the site total and one in each channel). The key factor shares, the 25% / 50% gates and the reconciliation `opening_sessions + Σ delta + residual_delta = closing_sessions` all depend on that additivity.

**The one exception: Search Console clicks.** Search query figures (`search_query_shifts`, `search_clicks`, the `Search keyword` sub-row) count clicks, are labelled as clicks, and are never divided by or compared with visits. Every keyword test is taken against the site's total Search Console click change (`contextual_data.search_clicks`). A keyword is never a card and is never ranked among visit items.

**Naming.** No figure is ever called visitors, users or people, in any language. The "Visitor type" sub-row (GA4 `newVsReturning`) keeps its name because it names a dimension; its figure is visits, and the prompt renames its value to `new-visitor visits` / `returning-visitor visits` so the noun is visits. Conversion insights are a separate feature and are unaffected.

**Enforcement.** `internal/ai/visits_unit_guard_test.go` scans the benchmarking code, prompt, examples, judge, synthetic corpus, golden set, CLI, controller, Postman collection and this document for a person unit; the golden set's units are checked by `internal/ai/eval/goldenset_units_test.go`; a test requires, on every real checkpoint, that the period visit totals equal the channel partition's totals; `check-sites` fails a published narrative that labels a count as visitors.

## 4. Request Schema

`POST /v1/ai/benchmarking?hl=<locale>`

| Part | Content |
| :--- | :--- |
| `Authorization` header | `Bearer <OAuth access token>` of a Google user registered on the site. Missing: 403 `missing authorization`; not a `Bearer` value: 403 `invalid authorization`; token rejected: 403 `invalid authentication token`; user not on the site: 403 `user not found`. |
| `User-Agent` header | The plugin's application name, `wordpress/google-site-kit/<GOOGLESITEKIT_VERSION>` (`wordpress-multisite/…` on multisite), as `Google_Proxy::get_application_name()` builds it. Optional and never a reason to reject: when it parses (`traits.ApplicationNameLoader`), its platform and release are recorded on the interaction row (`platform_name`, `platform_version`) and in the logs of ignored inputs, so a payload can be tied to the plugin release that computed it. `Google_Proxy::request()` sets no `User-Agent` today, so the plugin's benchmarking proxy method must set it. |
| `Content-Type` header | `application/json`. The body is read only for that media type and is capped at 2 MiB: a larger body is 400 `request body too large`, malformed JSON is 400 `failed to parse json body: <detail>` (both coded `INVALID_ARGUMENT`). Unknown fields are ignored. Every integer field accepts a JSON number that holds a whole value written as a float (`1234.0`, `1e3`), the way PHP's `json_encode` writes a float; a fraction (`1234.5`) in an integer field still fails to parse, and so does a whole-number literal longer than 64 bytes or with an exponent beyond ±30, which is left as sent rather than expanded (`internal/utils/jsonnumbers`). |
| `hl` query parameter | Locale of the narrative, as WordPress sends it (`get_user_locale()`: `de_DE`, `es_MX`, `de_DE_formal`, `zh_TW`) or as a BCP-47 tag (`de-DE`); defaults to `en`. The endpoint resolves it to a language (§7.6.1): every English variant gets the English-only output schema, every other locale an insight in its language, with the glossary for all 20 Tier 1 languages (`de`, `es`, `fr`, `it`, `pt`, `id`, `tr`, `ko`, `pl`, `ja`, `gl`, `uk`, `sr`, `cs`, `ru`, `vi`, `nl`, `ar`, `hu` and `sv`, all variants, Serbian in Latin script (`sr_Latn`, `sr_ME`) with its glossary transliterated) and the generic translation rules for every other language. A locale that names no language falls back to English. |
| Body | JSON, below. |

The checks run in this order and the first failure is returned as `{"error": "<message>", "code": "<code>"}` (§6.3): the body parses (at most 2 MiB of JSON, decoded before the request is authenticated); the `Authorization` header is present and a `Bearer` value; the required core passes the table below (in table order, HTTP 400); the site exists (otherwise 400 `Unable to retrieve site connection. You may need to perform a plugin reset.`, coded `SITE_NOT_FOUND`) and `site_secret` matches it (otherwise 400 `invalid 'site_secret'`); the token is valid and its user is on the site (403); a cached response is returned if there is one (§6.1); a claim on the cache key (409 `GENERATION_IN_PROGRESS` while an identical request generates); a generation slot (503 `SERVICE_BUSY`); the rate limit (429 `RATE_LIMITED` or `DAILY_CAP`); then generation (§7.1).

**The required core** keeps its 400s, since without it nothing can be written:

| Field | Type | Constraints | Error |
| :--- | :--- | :--- | :--- |
| `site_id` | string | non-empty | `missing parameter: 'site_id'` |
| `site_secret` | string | non-empty; must match the site (checked after this table) | `missing parameter: 'site_secret'` / `invalid 'site_secret'` |
| `end_date` | string | non-empty | `missing parameter: 'end_date'` |
| | | a `YYYY-MM-DD` calendar date (`ai.EndDateError`) | `invalid parameter: 'end_date' must be a YYYY-MM-DD date` |
| | | no later than the day after today's UTC date (a site ahead of UTC may already be on it) | `invalid parameter: 'end_date' is in the future` |
| `days_in_period` | integer | 7–364; the dashboards send the header range (7, 14, 28 or 90) | `invalid parameter: 'days_in_period'` |
| `visits` | object (§4.1) | neither `current_period` nor `previous_period` negative | `invalid parameter: 'visits'` |
| | | `current_period` and `previous_period` not both 0 | `missing parameter: 'visits'`, coded `NO_DATA` |

**Every optional input is screened, never rejected** (§5.10 *Endpoint screening* for `decomposition`). The endpoint keeps what it can use, ignores the smallest invalid unit, never corrects a number, and logs what it ignored, with the plugin release, as one warning (`event: benchmarking_inputs_ignored`). An older or newer plugin whose output the endpoint finds partly wrong loses only the affected part of the narrative, never the whole insight:

| Received | Endpoint action | Narrative effect |
| :--- | :--- | :--- |
| `baseline` with one bound or both missing, a negative bound, or `min > max` | Ignore the range (the two bounds only mean something together) | Status `NO_RANGE`: *"we're still learning what's usual for your site"* |
| A valid but implausible `baseline` (`BaselinePlausibilityIssues`) | Keep, and log | Narrated as sent |
| `visits.last_year` with a total missing or negative | Ignore `last_year` | No last-year clause |
| A negative `history_days` | Ignore it | No check-back clause |
| A contextual row whose `sessions`, `clicks` or `visits` count is negative; a negative `search_clicks` total | Drop the row (the total) | The row is not narrated |
| A contextual list longer than its limit | Keep the rows that moved most (by \|current − previous\|; by visits for `recent_content_momentum` and the top pages), in the order sent (`ai.LimitContextualRows`): `recent_content_momentum` 50, `search_query_shifts` 100, `traffic_channel_surges` 50, `user_mix_shifts` 50, `referrers` 100, `device_shifts` 50, `channel_breakdowns` 1,000, `channel_pages` 10,000, `channel_campaigns` 100, `top_pages` and `previous_top_pages` 50 each | Only the rows kept are narrated; a limit can change without breaking a client |
| `decomposition` | Screened field by field (§5.10) | Only the usable subset is narrated |
| `in_period_spike` | Optional `{peak_date, start_date, end_date, days, share_of_gain_pct}` computed by the client when a contiguous 1–3 calendar-day run exceeds the daily upper bound and accounts for ≥ 40% of a positive period delta; `Sanitize` validates `YYYY-MM-DD` dates (`start_date ≤ peak_date ≤ end_date`), `1 ≤ days ≤ 3`, and finite `0 < share_of_gain_pct ≤ 100`, dropping malformed values | Forwarded to `trends.in_period_spike` so `analysis` notes the brief spike |
| `async` | `true` returns an operation (§6.2) | — |

A request whose `visits.current_period` and `visits.previous_period` are both 0 has no period comparison to narrate, so it is rejected with 400 `missing parameter: 'visits'`, coded `NO_DATA`: a normal state (a new site, a broken tag) the client can tell apart from a malformed request. This covers a request with no `visits` object at all. Fields of the previous contract (`visits.current_week` / `previous_week`, `baseline.period_months`, `trend_direction`, `is_seasonal_period`, `model_version`) are ignored like any unknown field, so an older client's request is judged on the fields that remain; a legacy baseline sent without range bounds is ignored like any other baseline without both bounds.

### 4.1 `visits`

```json
{"current_period": 1250, "previous_period": 1000, "last_year": {"current_period": 1100, "previous_period": 900}}
```

All integers, all visits (GA4 `sessions`) over the windows of §5.1. There is no `visitors` alias: a request that sends its totals under any other key is a 400. `last_year` holds the same two windows 364 days earlier (§5.5); the client omits it when its daily series does not cover both windows. The endpoint uses it only to decide `repeat_last_year` (§7.4); its figures are never sent to the model or narrated.

### 4.2 `baseline`

```json
{"expected_range_min": 1020, "expected_range_max": 1110}
```

| Field | Type | Meaning |
| :--- | :--- | :--- |
| `expected_range_min`, `expected_range_max` | integer | The band of normal for a `d`-day total, forecast from the history before the period (§5.4); neither is negative and `min ≤ max` (§4) |

Omit `baseline` while the site has under `d + 55` days of history (the period's first day needs 56 days up to and including itself for its 28-day fit; §5.4 Step 1 and *Request range*): the status is then `NO_RANGE` and the analysis says *"…, while we're still learning what's usual for your site."* Send `history_days` with such a request: the days of daily history the client holds up to and including `end_date`. The endpoint then computes `weeks_until_range` = ⌈(`d` + 55 − `history_days`) / 7⌉ (`WeeksUntilRange`; `d + 55` is §5.4's minimum history for a range, `MinBandHistoryDays`) and the analysis adds *"; check back in about N weeks"* in the same sentence (*"within a week"* for one, since one week rounds up anything from a day to a week; in ja-JP and ko-KR the clause is a parenthesis before the sentence's end, so the analysis stays one sentence). Without `history_days`, or with enough history, no time is stated. A `baseline` without both bounds, with a negative bound or with `min > max` is ignored and logged (§4), and the period is narrated as `NO_RANGE`. The bounds are part of the response cache key and of the recorded payload, and are never sent to the model: the model receives the status and the distance (§7.4), never a bound.

**Plausibility.** A valid but implausible range is **logged, not rejected** (`logBaselinePlausibility`, `BaselinePlausibilityIssues`): a center outside 0.2–5× `visits.previous_period`, or a half-width outside 5–100% of the center, writes a warning, so a client whose baseline diverges from the reference model shows up in production logs. The bounds arrive rounded and with the minimum floored at 0, so the half-width check runs against their midpoint and its upper limit cannot fire (a floored minimum gives exactly 100%).

### 4.3 `contextual_data`

Every GA4 figure is visits under the key `sessions` as `{current, previous}` (a plain integer on `recent_content_momentum`). Every field is optional; a missing field means "no data", never zero. String fields may be sent raw: the endpoint and the card computation sanitize them (§5.9). A row with a negative count, or a `search_query_shifts` row whose `position` is not finite, negative or above 1,000,000, is dropped and a list over its limit is trimmed to the rows that moved most (§4), never rejected.

| Field | Row shape | Used for |
| :--- | :--- | :--- |
| `traffic_channel_surges` | `{channel, sessions}` (and optionally the reduced fields of §5.9, normally left empty) | Cards, ranked impacts, scenario |
| `channel_breakdowns` | `{channel, device, segment, sessions}` | Reduced to each channel's device and visitor type, then dropped |
| `channel_pages` | `{channel, url, sessions}` | Reduced to each channel's landing page and Direct's homepage share, then dropped |
| `channel_campaigns` | `{channel, campaign, sessions}` | Campaign sub-rows on Email, social and paid cards; never in the prompt |
| `referrers` | `{referrer, sessions}` | Referring-site and campaign children, ranked impacts, scenario |
| `device_shifts` | `{device, url?, sessions}` | Ranked impacts, narrative |
| `user_mix_shifts` | `{segment, url?, sessions}` | Ranked impacts, narrative |
| `search_query_shifts` | `{query, url?, clicks: {current, previous}, position: {current, previous}}` | `Search keyword` sub-row, scenario, narrative |
| `search_clicks` | `{current, previous}` (integers ≥ 0) | Denominator of the keyword sub-row and of the search-query scenario; never in the prompt |
| `recent_content_momentum` | `{url, title, published_days_ago, sessions}` | Content cards, scenario, narrative |
| `top_pages`, `previous_top_pages` | `{url, visits, categories[]}` (the 50 most visited are kept) | Category counts derived by the endpoint (§7.3), then dropped |

`category_resonance` is not a request field: the endpoint derives it from `top_pages` and `previous_top_pages` and discards any value the client sends.

## 5. From GA4, Search Console and WordPress to the Request (Client)

The client prepares everything the endpoint compares, plus the cards the reader sees:

1. Retrieve the reports (§5.2).
2. Sum the period totals and last year's totals for the same windows (§5.3, §5.5).
3. Compute the expected range (§5.4) and draw the chart corridor (§5.6).
4. Build the contextual rows (§5.7).
5. Classify the landing pages it may show (§5.8).
6. Compute the key factor cards on a sanitized copy of the rows (§5.9, §5.10), render them, and send them as `decomposition`.

Classification (5) must run on the raw rows, before any reduction, so a hidden top page leaves its channel's next page available.

### 5.1 Windows

**Requirements.** Both compared periods have the same length `d`, the header range the reader picked, and end on consecutive days; every figure in the request is computed over the same windows.

**Design.** `T` is `end_date`, `d` is `days_in_period`.

| Window | Range |
| :--- | :--- |
| Current period | `[T − d + 1, T]` |
| Previous period | `[T − 2d + 1, T − d]` |
| Baseline reference | for each day `t` of the current period, the up to 365 days up to `t − 28`, `[t − 392, t − 28]` (fewer when the history is shorter; §5.4 *Request range*) |
| Last-year windows (`visits.last_year`) | the current and previous periods shifted back 364 days (52 weeks, so weekdays line up): `[T − 364 − d + 1, T − 364]` and `[T − 364 − 2d + 1, T − 364 − d]` |

A client sending `d ≠ 28` computes everything on `d`-day windows, the baseline included (its range is for the `d`-day total, §5.4 *Request range*): the endpoint compares whatever totals it receives, so a 28-day range against a 90-day total reads as far above the range. Counts tuned on 28-day totals scale as `round(n × d / 28)` (at least 1); percentages do not.

### 5.2 Reports

All GA4 reports use the metric `sessions`. "Both periods" means the current and previous period of §5.1 (one report with two date ranges, or two reports). The Go client reads complete daily exports, so its top-N cuts are exact; a client that limits a report must fetch enough rows that the cut in §5.7 is unaffected.

| # | Source | Dimensions | Dates | Feeds |
| :--- | :--- | :--- | :--- | :--- |
| 1 | GA4 | `date` | the last `max(d + 392, 364 + 2d)` days ending at `T` (420 at 28, 482 at 90; covers the first day's 365-day reference, which ends at `T − d − 27`, and the last-year windows) | `visits`, `baseline`, chart |
| 2 | GA4 | `sessionDefaultChannelGroup` | both periods | `traffic_channel_surges` |
| 3 | GA4 | `sessionDefaultChannelGroup`, `deviceCategory`, `newVsReturning` | both periods | `channel_breakdowns` |
| 4 | GA4 | `sessionDefaultChannelGroup`, `landingPagePlusQueryString` | both periods | `channel_pages` |
| 5 | GA4 | `sessionDefaultChannelGroup`, `sessionCampaignName` | both periods | `channel_campaigns` |
| 6 | GA4 | `sessionSource` | both periods | `referrers` |
| 7 | GA4 | `deviceCategory` | both periods | `device_shifts` |
| 8 | GA4 | `newVsReturning` | both periods | `user_mix_shifts` |
| 9 | GA4 | `landingPagePlusQueryString` | both periods | `recent_content_momentum`, `top_pages`, `previous_top_pages` |
| 10 | Search Console Search Analytics | `query` (clicks, position) | both periods | `search_query_shifts` |

### 5.3 Site Totals (`visits`)

**Requirements.** The two totals, and the two `last_year` totals, are the site's visits in the windows of §5.1, from the same daily series the chart plots and the range is fitted on.

**Design.** Each total is the sum of report 1 over its window. Offline, the daily series is the per-day sum of the channel export (every session has one channel, so the sum is the day's sessions); a day missing inside the export is a load error, and a window the series does not cover fails the request build.

### 5.4 Expected Range (`baseline`)

**Requirements.**
- Answer one question: *is this period's total within the range of how the site usually performs?* The range is therefore a **forecast**: each day of the period is forecast from the history at least 28 days before it (*Request range* below), so for a period of up to 28 days nothing inside the period can move it, and it can place a period outside it in either direction. For a longer period, its later days are forecast partly from its earlier days.
- Resist spikes, surges and tracking outages of up to about four weeks (they are removed before fitting, from both the level and the misses; Step 2 states how reliably under day-to-day noise), center on the site's long-term usual level rather than its last few weeks, carry part of its long-term trend, and widen the band for sites whose own period-to-period forecasts missed by more, without making it meaninglessly wide. No width cap and no `NO_RANGE` fallback: the range is narrowed only by removing what is not usual traffic. Target: about 80% of periods within the range, calibrated at `d = 28`; the current model measures 71.7% at 28 days on the four frozen sites, a documented trade-off (*Model choice* below).
- Be portable: the Go code is the reference implementation the PHP client ports, and every constant and rounding rule below is part of the specification.

**Reference and acceptance suite.** The Go implementation is `computeBaselineModelForPeriod` in `internal/ai/baseline_model.go` (one fit, Steps 0–7) and `fitDailyRange` in `internal/ai/expected_range.go` (the request range from one 28-day fit per day, *Request range* below), with `CalculateRobustBaselineForPeriod` returning the request's `baseline`. The acceptance suite is the set of language-neutral fixtures in `internal/ai/testdata/baseline_conformance/*.json` (checked by `TestBaselineConformance`), each at its own `days_in_period` (28 unless stated). Each fixture holds a contiguous daily series (`start_date`, `daily_visits`), the target date `T`, the `baseline` object the request must carry, the `range` (`center`, `margin` and, per day of the period, `center`, `half_width`, `expected_min` and `expected_max`; null without a range), and the intermediate values of the 28-day fit ending on `T` (`model`, null under 56 days): `filtered_days` (the dates the spike filter replaced), `block_totals` (raw, informational), `cleaned_block_totals`, `ratios` (drift), `width_ratios` and `level` of the uncut reference, `alignment_drifts`, `alignment_centers` and `alignment_margins` of the four alignments, `block_center`, `period_weight`, `center`, `margin` and `dow_factors_sunday_first`. A client conforms when it reproduces every fixture's `baseline` and daily bounds exactly, its `filtered_days` exactly and its other intermediates within `1e-6`. The fixtures cover 0, 27, 55, 56, 82, 83, 84, 110, 111, 139, 140, 365 and 420 days of history, a history that is not a whole number of blocks, a zero block, a flat site, a spike month, a four-week surge ending the reference (`spike_4w_removed`), a five-week surge that is kept (`surge_5w_kept`), a two-week outage (`outage_2w`), a four-week outage ending the end date's fit reference under ±20% week-to-week noise at `d = 7` (`outage_4w_week_noise`), a two-block dip followed by a return (`dip_return`), a step the alignments cut differently (`grid_shift`), a step drop and a seasonal period at `d = 28`, periods of 7, 10, 14, 90 (a growing site whose four alignments all measure a drift) and 182 days with the first day each gets a range, and the `last_year` totals (each fixture also carries the `visits.last_year` the request must send, or none). Regenerate them after an intended model change with `go test ./internal/ai/ -run TestBaselineConformance -update-baseline-conformance`.

**Design.** The model always fits **28-day blocks**, whatever the judged period's length `d`, and then scales the fitted band to the period (Step 5). `T` is the last day of the judged period `[T − d + 1, T]`; the **reference** is the history before its first day `T − d + 1`, limited to its last `R = 365` days. The constants (the 365-day cap, the 0/7/14/21-day alignments, the one-block minimum reference) do not depend on `d`.

*Porting note.* This replaces the period-scaled blocks of the first multi-period version (blocks of `d` days, a `3d`-day minimum history, a `max(365, 2d)` reference and a `⌊d / 4⌋` alignment step). With `d`-day blocks a 90-day reference of 365 days held only four blocks, three of the four alignments had too few ratios to measure a drift, and growing sites read above their range; a 7-day block learned its level from week-to-week noise. A client ported from that version must rebuild against the current fixtures: at `d = 28` nothing changes (the fixtures only gain `block_center` and `period_weight`), at every other `d` the range, the minimum history and the daily band change.

**Step 0: Inputs.** A contiguous daily series of visits (report 1, GA4 `date` dimension, property timezone), ending at `T`, with missing days filled with 0; weekday and day-offset arithmetic runs on calendar dates, not on timestamps. The Go reference builds this series itself from the rows it is given (`dailySeriesThrough`): from the earliest row through `T`, a missing day (a gap, or lagging rows that stop before `T`) is 0 and a duplicated date keeps its last row, so the reference always ends the day before the judged period. `T` is the last complete day: a partial day lowers the judged total and fakes a drop.

**Step 1: History tiers.** `n` is the number of days up to and including `T`.

| `n` | `baseline` in the request | Range | Narrative |
| :--- | :--- | :--- | :--- |
| 0 to `d + 54` (0–82 at 28) | omitted | — | `NO_RANGE`: "…, while we're still learning what's usual for your site." (plus "; check back in about N weeks" with `history_days`, §4.2) |
| `d + 55` to `d + 82` (83–110 at 28) | present, with both range bounds | present (`EarlyBand = true` on `ExpectedRangeSeries`: at least one day uses 1 reference block) | range status phrase (§7.6) |
| `d + 83` or more (111+ at 28) | present, with both range bounds | present (`EarlyBand = false`: every day has ≥ 2 reference blocks) | range status phrase (§7.6) |

Steps 2–7 describe one fit: the model for a period ending on a given day, fitted on the reference before that period. The request's range is built from one such fit per day of the period, each a 28-day fit (*Request range* below); a fit needs one 28-day reference block before its period (`MinRangeHistoryDays = p + 28` for a fit of `p` days, 56 for the 28-day fit), which is why a range needs `d + 55` days (`MinBandHistoryDays`).

**Step 2: Spike filter and cleaned values** (on the reference only, once). A same-weekday Hampel filter: each day is compared with the values on the same weekday around it, and replaced when it is far from them by more than the reference's own day-to-day noise. On the reference values `v[0..r−1]` (oldest first; the weekday is the index modulo 7, since the series is contiguous):
```text
W = 4 (weeks), k = 4
for each day i:
    S       = the indices i mod 7, i mod 7 + 7, ... < r          (same weekday as i, oldest first)
    N       = min(2W + 1, |S|)                                   (9 values, 57 days)
    pos     = floor(i / 7)                                       (position of i in S)
    start   = min(max(pos - W, 0), |S| - N)                      (window shifted to stay inside the reference)
    win[i]  = S[start .. start + N - 1]                          (raw values: the filter is not recursive)
    med[i]  = median(v[win[i]])                                  (only when N >= 5: a shorter window never cleans)
sigma   = 1.4826 * median(|v[i] / med[i] - 1| for the days i with N >= 5 and med[i] > 0)
          (0 when there are none: one relative noise level for the whole reference)
wdMed[w]= median(v[j] for j with j mod 7 == w)                   (overall reference median for weekday w)
trough[i] = v[i] > med[i] and wdMed[i mod 7] > med[i]           (a high value inside a local trough)
thr(m)  = k * max(sigma * m, sqrt(max(m, 1)))                    (Poisson floor)
flag[i] = N >= 5 and (v[i] - wdMed[i mod 7] > thr(wdMed[i mod 7])   when trough[i]   (one-sided)
                      |v[i] - med[i]| > thr(med[i])                 otherwise)
v~[i]   = median(v[j] for j in win[i] with flag[j] false)   when flag[i]   (med[i] when every j is flagged)
        = v[i]                                               otherwise
filtered_days = the dates of the days where v~[i] != v[i]
```
A run of up to `W` same-weekday values is a minority of its 9-value window, so the window median stays near the usual level; a run of `W + 1` or more moves the median and is kept as a real level change, so a real step younger than about four weeks is treated as a spike until it persists. When a day sits above its local 9-week window median while that window median is in a trough below the weekday's overall reference median (`wdMed[i mod 7] > med[i]`), measuring the high-side threshold against `wdMed[i mod 7]` keeps ordinary return-to-normal days at the end of a multi-week dip from being falsely erased as spikes. That test is one-sided (only a value above `wdMed[i mod 7]` by more than the threshold is a spike): an ordinary day in the upper half of a long trough sits below `wdMed` and is kept, where a two-sided test flagged it as an outage of the year-wide level and replaced it with the trough's lower half (14 of 18 upper-half days in a 15-week trough, cleaned blocks 4.1% low). No mirrored low-side switch is needed: a normal day next to a surge has at most `W` surge values in its 9-value window, so its window median stays at the normal level. The deviation is the reference's own noise (`sigma`, one value per reference, from about a year of days), not the spread of the 9-value window: with three or four of the nine values in a run, the window's MAD would be the whole spread of the five normal values, and under 10–20% day-to-day noise most 3–4 week runs would survive (the first version of this filter, iteration 1 of the v13 fixes, removed a 4-week outage about 38% of the time at 10% noise and 5% at 20%). The replacement is the median of the window's unflagged values, because with four outliers the plain window median is the edge of the five normal values. Envelope on synthetic 365-day references (`_rangereplay -study`, share of the run's extra or missing volume removed, worse of mid-reference and reference end): outages (×0) of 2–4 weeks 93–98% at every noise level up to 20%; 2× surges of 2–4 weeks 97% at 10% day noise, 74–90% with 10% week-level plus 10% day noise, and only 47–78% at 20% day noise (a 2× day is then often within 4σ of the window median); moves of 5–8 weeks keep at least 88% of their volume; on event-free series about 0.1–0.2% of days are replaced and 28-day block volumes move by 0.04–0.12%. Same-weekday windows never flag a weekday/weekend pattern, and the `√median` floor leaves flat and low-traffic series untouched. The cleaned values are used everywhere below: blocks, level, misses, drift and weekday factors.

*Known limitation:* the reference is cleaned but the judged period's total is raw (Step 1 judges the period's actual visits). Days the filter removes from the reference (surges, promo days, a monthly newsletter or payday peak) stay in the judged total, so a site whose events recur less often than weekly reads somewhat above its range on average; on high-traffic sites with small `sigma` this is part of why within sits at 71.7% across the four frozen sites (*Current model* below).

**Step 3: Reference blocks.** Non-overlapping 28-day blocks aligned **back from the end of the reference** (`T − d` for the uncut reference): at `d = 28` the last block is `[T − 55, T − 28]`, the one before it `[T − 83, T − 56]`, and so on. Only complete blocks inside the reference are used; leftover days at its start are ignored. With `d + 56` days of history there are 2 blocks; with `d + 365` or more there are 13. For each block `k = 1..m` (oldest first): `B~_k` is the **cleaned** total, used for every forecast and outcome; the raw total `B_k` is kept for information only (the fixtures' `block_totals`).

**Step 4: Center** (per alignment; the band is the median over the alignments, Step 5).
```text
W_k         = B~_{max(1, k-11)} .. B~_k               last 12 cleaned blocks (fewer at the start), med_k = median(W_k)
level(k)    = median(b in W_k with b >= 0.75 * med_k) when |W_k| >= 8, B~_k >= 0.75 * med_k (the latest block has recovered)
              and more than |W_k|/2 blocks >= 0.75 * med_k, else med_k
r_k         = B~_k / level(k - 1)                     for k = 2..m; skipped when level(k - 1) = 0   (drift ratios)
d_raw       = median(r_k) when there are at least 3, otherwise 1
d           = 1 when m >= 8 and d_raw < 1, else d_raw
center      = max(10, level(m) * (1 + 0.5 * (d - 1)))   (half the measured drift; a 28-day block center)
```
The level is the long-term usual volume: a dip or surge of several weeks or a 10-week seasonal trough no longer becomes the new "usual", and a lasting change stops being flagged once it spans most of the 12 blocks. When at least 8 blocks of history exist, trimming minority trough blocks below `0.75 × med_k` and clamping downward drift to `1` keeps a multi-block winter slump from pulling the return-to-normal level below the rest of the year. The trim applies only once the trough is over, when the latest block is back at `0.75 × med_k` or more: while it is still low the drop is current, and trimming the new, lower blocks held a permanent 40–50% drop at the old range for seven periods (it now moves in the seventh; the 12-block median itself needs about half its window, so the range reaches the new level from the eighth). The drift clamp does not wait for recovery: a trough the judged period returns from looks the same in the reference as a drop that goes on, and keeping the downward drift there read shop.merch's return to normal on 2026-03-18 as above the range. "Usually" includes part of the site's long-term trend: the drift carries it into the center, but only half of it, because a full median drift over-extrapolates turns and moves the band from week to week. The median of an even count is the mean of its two middle values.

**Step 5: Width (`margin`) and the four alignments.** The misses measure period-to-period noise of the cleaned series, against a one-step forecast, while the center carries the long-term level. Each miss deviation is Winsorized at `0.19` (`baselineMaxWidthMiss`) so multi-week surges/campaigns (>28 days) do not inflate the expected range width to near-zero lower bounds:
```text
f(k)        = (3 * B~_k + 2 * B~_{k-1} + 1 * B~_{k-2}) / 6
              one-step forecast, newest heaviest, over the blocks that exist
              (fewer at the start: (3 * B~_k + 2 * B~_{k-1}) / 5, then B~_k)
e_k         = B~_k / f(k - 1) - 1                     for k = 2..m; skipped when f(k - 1) = 0   (width_ratios - 1)
K           = number of e_k
sigma_site  = 1.4826 * median(min(|e_k - median(e)|, 0.19))   when K >= 3
            = sqrt(mean(min(|e_k|, 0.19)^2))                  when K = 1 or 2
            = 0                                               when K = 0
floorMargin = 5 * sqrt(center) + 0.13 * center
sigma0      = floorMargin / center / 1.645
sigma       = sqrt((n0 * sigma0^2 + K * sigma_site^2) / (n0 + K)),   n0 = 4
margin      = max(15, center * z * sigma),   z = 2.326

weight      = 7 * floor(d / 7) + sum of dow(w) over the d - 7 * floor(d / 7) leftover days   (Step 6)
              the period's length in weekday-weighted days: exactly d when d is a multiple of 7;
              the leftover days are the last ones of the period, [T - d + 1 + 7 * floor(d / 7), T]

for j = 0, 1, 2, 3:                          (four block alignments, 7 days apart)
    R_j = the cleaned reference of Step 2 without its last 7 * j days   (skipped when R_j has fewer than 28 days)
    blocks aligned back from the end of R_j (Step 3); d_j and center_j (Step 4) on R_j alone
    margin_j = margin (above) for the center center_j * weight / 28 and the misses e_k of R_j
block_center = median(center_j)              (R_0, the full reference, always exists)
center = block_center / 28 * weight          (the daily rate over the period's days)
margin = median(margin_j)

expected_range_min = max(0, round(center - margin))
expected_range_max = round(center + margin)
```
The period's center is the 28-day daily rate (`block_center / 28`, the same for every `d` on the same first day) over the period's weighted days, so the drift enters it once, whatever the period's length. Its width keeps the relative spread `sigma` of the 28-day misses; the size default (`floorMargin`) and the 15-visit minimum are evaluated on the period's own center, so a short period on a small site is relatively wider than a 28-day one (Poisson noise). The filter runs once on the full reference and each alignment cuts the cleaned series (it stays out of sample: the filter only reads days before the judged period). Fitting the center and the margin on every alignment makes the band independent of where the block grid happens to cut the reference, so a one-week shift no longer moves the bounds. The fixtures' `level`, `ratios` and `width_ratios` are those of `R_0`. Rounding is half away from zero, and the bounds are sent as **integers**: in PHP `(int) round(...)`, so the request carries whole counts (the endpoint also accepts `1234.0`, which `json_encode` emits for a float, but rejects a fraction such as `1234.5`; §4). The size default `sigma0` keeps its 1.645 divisor, so without misses the margin is the size floor scaled by 2.326 / 1.645 (about 1.41 × `floorMargin`); with 12 months of history the site's own misses carry about 70–75% of the weight. The band is symmetric around the center, and flags are uneven (more above than below) because growth surprises are larger than drops; this is accepted.

**Step 6: Day-of-week factors** (`dow`, chart only), on the cleaned reference values:
```text
mean(w)  = mean of v~(t) over the reference days with weekday w     (0 = Sunday .. 6 = Saturday)
M        = mean of mean(w) over the weekdays that have samples
dow(w)   = 0.10 + 0.90 * mean(w) / M
```
A weekday without samples gets 1.0, and every weekday gets 1.0 when `M` is 0. The factors average to 1 over a week. They weight a period's leftover days (Step 5) and spread the band onto the chart's days: a day's band is `max(0, center ± margin) × dow(w) / weight`, rounded to one decimal, so the period's days add up to its band.

**Step 7: Guards (porting rules).** Every division is guarded: a zero level skips its drift ratio and a zero forecast its miss; an alignment shorter than 28 days is skipped; `center ≥ 10` (on the 28-day block center); `margin ≥ 15` (on the period's margin). A filter window of fewer than five same-weekday values never cleans (days 28–34 of a single-block reference have 4 values per weekday and skip cleaning; the filter activates from day 35+); the window shifts to stay inside the reference; `sigma` is 0 when no day has a window with a positive median, and the deviation is floored at `√max(median, 1)`; a flagged day whose window values are all flagged takes the window median. All outputs are finite for an all-zero history, a zero block or a zero level. Median of an even count is the mean of the two middle values. Range bounds are integers (Step 5).

**Request range (daily fits, fixed 28-day lag).** The request's range and the chart's band (§5.6) come from the same fits (`fitDailyRange` in `internal/ai/expected_range.go`; `CalculateRobustBaselineForPeriod` returns its range). Each day `t` of the period `[T − d + 1, T]` gets its own fit: the model above for the 28 days ending on `t` (Steps 2–7 with `T = t` and `d = 28`), fitted on the up to 365 days up to `t − 28`. So a day is always forecast from the history at least 28 days before it, whatever range it is viewed in, and no day of a period of up to 28 days feeds any day's band of that period:
```text
c_t = block_center_t / 28 × dow_t(weekday(t))          (the day's center)
h_t = margin_t × dow_t(weekday(t)) / 28                (its raw half-width; period_weight is 28)
C   = Σ c_t                                            (the total's center)
M   = median over the alignments j of T's fit:
        baselineMargin(C × alignment_center_j / block_center, misses_j)   (Step 5 on the total's center)
h'_t = h_t × M / Σ h_t                                 (M / d each when Σ h_t is 0)
baseline = [max(0, round(C − M)), round(C + M)]        (round half away from zero)
```
`M` is the end date's fit's margin for a total centered on `C`: it keeps the model's calibration (the 28-day misses' relative spread, the traffic-size default on the total's center and the 15-visit minimum), so a 7-day total gets a relatively wider range than a 28-day one and a 90-day total a narrower one; for the fit's own period center it is the fit's margin. Scaling the half-widths makes the chart's daily bands add up to the request's range, so the chart and the verdict never disagree. A range needs every day's fit, so its first day needs 56 days up to and including itself: `MinBandHistoryDays = d + 55` (83 at 28, 62 at 7, 69 at 14, 145 at 90), and the longest period with a range is `MaxRangePeriodDays = history − 55`, so `d = 364` gets a range from 419 days of history. During days `d + 55` through `d + 82` (days 83–110 at 28), at least one day of the range is fitted on a single 28-day reference block (`ExpectedRangeSeries.EarlyBand = true`). For a period longer than 28 days, its later days are fitted partly on its earlier days, so a shift that lasts several weeks is gradually carried into the later days' bands (the trade-off of the fixed lag). There is no upper limit on the range length (decided Nov 18): every range from 7 to 364 days gets a band and a range once its history suffices, although on long ranges most days are fitted partly on the range itself (69% of the days at 90 days, 92% at 364).

### 5.5 Last Year's Totals (`visits.last_year`)

**Requirements.** Let the analysis add one fact when the period sits outside its range: that at this time last year traffic moved the same way, by a comparable margin. It must never claim a recurring or seasonal pattern, a cause, or that the period is normal for the time of year.

**Design.** The client sends the visits of the current and previous windows shifted back 364 days (§5.1) when its daily series covers all four windows, and omits `last_year` otherwise (`ai.LastYearVisitsFor`). The endpoint decides (`RepeatLastYear`), comparing last year's period-over-period move with this year's relative band width:

```text
w_now  = (expected_range_max − expected_range_min) / (expected_range_max + expected_range_min)
dev_ly = last_year.current_period / last_year.previous_period − 1
repeat_last_year = (ABOVE_EXPECTED and dev_ly > 0 and dev_ly ≥ +w_now) or (BELOW_EXPECTED and dev_ly < 0 and dev_ly ≤ −w_now)
```

It is false within the range, for `NO_RANGE`, without `last_year` and when `last_year.previous_period` is 0. The sign is required strictly, so a flat last year never repeats, even beside a zero-width range (`min == max`, whose `w_now` is 0). The comparison is made exactly in integers, by cross-multiplying the two ratios (`(cur_ly − prev_ly)·(max + min)` against `±(max − min)·prev_ly`), so a move exactly equal to the band width counts and a port in any language gets the same answer at the boundary. The verdict is sent to the model as `trends.repeat_last_year` (present only when true); the totals are never sent. The analysis then appends the fixed clause "…, and traffic also rose at this time last year." (`ABOVE_EXPECTED`) or "…, and traffic also fell at this time last year." (`BELOW_EXPECTED`), and states nothing else about last year.

### 5.6 Chart Corridor

**Requirements.** The Traffic chart shows daily visits against a shaded daily band of normal, following the site's weekday pattern. Each day's band is a forecast from the history at least 28 days before it, so a day's band center is the same in every range it is viewed in. The band is drawn on the whole range or not at all, and the days add up to the range the request's verdict used. The chart ends on `T`: it never shows predicted or future traffic.

**Design.** The plugin has no implementation of this part yet; it is specified here. The Go implementation is `ai.BuildExpectedRangeSeries`, which draws the band of §5.4 *Request range* for the `d` days ending on `T` and returns it with the request's `baseline` (`Baseline`), whether the band is drawn (`BandAvailable`), whether at least one day uses a single reference block (`EarlyBand`, days `d + 55` through `d + 82`), and the end date's fit reference length (`ReferenceDays`, for "Based on N weeks of your traffic").

```text
 Daily visits
       ▲
       │   day t's band: the 28-day fit for the days t-27..t,
       │   fitted on the days up to t-28 (at most 365)
       │      ├──────── reference ────────┤ ├── 28 days ──┤
       │                                  t-28           t
       └──────────────────────────────────────────────────┼──► Date
                                                          T
```

1. **Days** `[T − d + 1, T]`. Day `t` gets the center `c_t` and the scaled half-width `h'_t` of §5.4 *Request range*:
   ```text
   expected_min(t) = max(0, c_t - h'_t)
   expected_max(t) = c_t + h'_t                       (each rounded to 0.1)
   ```
2. **Whole range or none.** Under `d + 55` days of history up to `T` no day has a band (`expected_min` / `expected_max` are null) and the request has no `baseline`.

`go run ./cmd/insights export-chart-data` writes the full history of a frozen site, one row per day: the range of the period ending on the day (`Expected Range Min` / `Max`, `GenerateFullChartTimeseries`) and the band this chart draws for the day as that period's last day (`Daily Expected Min` / `Max`).

The verdict is about the period total, while the chart plots daily visits. Single days vary more than period totals, so the daily line can leave the band on some days of a period that is within range.

- Keep the payload bounded with deterministic top-N cuts (ties broken on the item's name, so the same data always yields the same request).
- Filter nothing beyond what is listed here: hygiene, classification and reduction (§5.8, §5.9) run on both sides from the raw rows.

### 5.8 Landing Page Classification

**Requirements.** A page a reader would not recognise is never shown as a card or a `Target page`: the homepage and its other addresses (`/home2`, the folder a site lives under), test and sample pages, deep pagination, feeds, admin and login pages. When a channel's top page is hidden, its next page takes its place. A page gets the same verdict every week, whatever its figures.

**Design.**

- **Verdicts.** `CONTENT` (the default, not stored), `HOMEPAGE`, `NON_CONTENT`. Hidden verdicts are kept per page key: the path in lower case without trailing slash. A page is *displayable* when it is not the root (empty, `/`, `/home`, `/index.html`, or an absolute URL without a path; query and fragment ignored) and is not classified `HOMEPAGE` or `NON_CONTENT`.
- **Pages classified**: for each channel that moved, its 5 largest `channel_pages` paths moving its way; search query URLs; recent content URLs (with their title). The root is excluded. At most 80, keeping the largest by visits.
- **Does the site have its own front page?** Yes when root rows carry at least 1% of the `channel_pages` visits (both periods), or of the `top_pages` visits when there are no channel pages; unknown without either. The rules below treat unknown as yes.
- **Rules**, first match wins, on the page key and title:
  1. Root → `HOMEPAGE`.
  2. `^/(home\d*|index(\.(html?|php))?|default(\.(html?|php))?|inicio)/?$` → `HOMEPAGE`.
  3. `NON_CONTENT`: a last segment `hello-world` or the title "Hello world!"; `/page/N` at the end with `N ≥ 2`; test pages (`tagtest`, `test_with_uid`, `hybrid_gaia`, a `test`, `tag-test` or `sandbox` segment, or "tagtest" in the title); `^/v0/b/` or `appspot.com`; a repeated `login` / `order` / `inbox` / `reviews` segment; `/feed`, `/rss`, `/atom` at the end; `/wp-admin`, `/wp-login`, `/xmlrpc.php`, `/cart`, `/checkout`, `/my-account`.
  4. A single-segment path (`/blog`, `/en`, `/search`): `/search` is `HOMEPAGE` on a site without its own front page and `NON_CONTENT` (internal search) on a site with one; any other single segment is `CONTENT` on a site with its own front page and **unresolved** on a site without one (it may be the folder the site lives under).
  5. Anything else → `CONTENT`.
- **Unresolved pages.** The Go client asks a small model (paths and titles only, a fixed list of known examples as guidance, temperature 0) and keeps only `HOMEPAGE` / `NON_CONTENT` verdicts for pages it asked about. The endpoint remembers each verdict the model gives for 7 days per site, across server instances, so a page is put to the model about once a week rather than on every generation (§7.2). The plugin has no model: it applies the rules and treats unresolved pages as `CONTENT`. On the real checkpoints the rules settle every page except one, Search Central's `/crawling` (a single-segment folder on a site without its own front page), which is `CONTENT` (the class the model gives a section folder, and the plugin's default), so the plugin's rule-only verdicts match.
- `top_pages` are not classified: a hidden page there has no category, so it can only take a slot in the top ten, never add to a count.

### 5.9 Preparing the Rows (Sanitization and Reduction)

**Requirements.** Before anything is shown or counted, user-generated text is made safe, sensitive and internal values are removed, equivalent rows are merged, and each channel's breakdown rows are reduced to the page, device and visitor type that carried its change, each with its own figure. The endpoint runs the same steps on its own copy for the prompt (§7.2), so the cards and the narrative see the same data.

**Design.** The client runs these steps on a deep copy of the request; the request it sends keeps the raw rows. *Text sanitizing* strips HTML and Markdown and normalizes control characters; *URL sanitizing* strips markup and control characters and removes the query string, fragment and credentials, and is never combined with Markdown stripping (which would rewrite valid paths). Truncation is by characters and is followed by trimming whitespace, so the value stays in sanitized form, which the card validation requires (§5.10).

1. Keep only `HOMEPAGE` / `NON_CONTENT` page verdicts; record whether the site has its own front page (§5.8) before the raw page rows are dropped.
2. `recent_content_momentum`: title text-sanitized, truncated to 100 characters, trimmed; URL URL-sanitized; drop entries whose URL is not displayable or whose title is sensitive or carries a marker the output safety check rejects (§5.10).
3. `search_query_shifts`: query text-sanitized; URL URL-sanitized and cleared when not displayable; drop sensitive queries and queries carrying a marker the output safety check rejects. Drop `search_clicks` if it has a negative value.
4. `traffic_channel_surges`: channel and device text-sanitized; segment text-sanitized, `established` → `returning`; `click_id_param` kept only when it is `fbclid`, `gclid`, `msclkid` or `mc_cid`; a URL already present becomes its normalized path, and is cleared with its `url_delta` when not displayable.
5. `top_pages` and `previous_top_pages` are folded into category counts and dropped (§7.3).
6. `user_mix_shifts`: segment sanitized and canonicalized, placeholders (`(not set)`, `(other)`, `unknown`, `(data not available)` and similar) dropped, rows with the same segment and URL summed. `device_shifts`: placeholders dropped.
7. `referrers`: drop placeholders, `(direct)`, internal, staging, CDN, scanner and audit-tool hosts and sensitive values (all tested on the text-sanitized form, since URL sanitizing percent-encodes `(not set)`), then keep the URL-sanitized form.
8. `channel_campaigns`: channel text-sanitized; campaign text-sanitized, truncated to 100 characters, trimmed; drop GA4 placeholders (`(not set)`, `(organic)`, `(referral)`, `(direct)`, `(cross-network)`, `(ai-assistant)` and any other single parenthesised token), sensitive names, and internal, personal or ID labels (dropped: `20103244`, `wnc_376106`, `Maria_20250417`, `Vinte e seis Elena|120236364496010746`; kept: `Summer 2024`, `Christmas 2025 Sale`); sum rows with the same channel and lower-case name.
9. **Channel reduction**, for each channel whose visits changed (`Δ ≠ 0`), matching breakdown rows to the channel by name, case-insensitively:
   - **Landing page** (only when the channel has no URL yet): before dropping empty/`(not set)` paths, record their summed delta on `not_set_landing_page_delta`, mark `has_channel_pages: true` when the channel has at least one non-`(not set)` landing-page row, and record `max_page_delta` as the largest same-direction non-homepage real-URL delta (including non-content pages, without the 10% floor; all three are internal to `direct_surge_pattern`, §7.4, and stripped before the prompt). Normalize each remaining `channel_pages` address to its path (query string removed; a recognised click-ID key noted); skip non-displayable paths; sum per path. The candidate is the path with the largest change in the channel's direction (ties: the smaller path). It is kept as `url` with `url_delta` = its change when `|d| / |Δ| ≥ 0.10` (no upper overrun cap: oversized pages where other pages moved the opposite way are kept and handled as oversized rows in §5.10). Only the largest candidate is tried: when it falls below 10%, no smaller page replaces it. `click_id_param` is set when that page's click-ID rows moved the channel's way by at least 25% of the page's change.
   - **Cross-channel pages**: before `channel_pages` is dropped, aggregate displayable landing-page deltas across all channels into `cross_channel_pages` (internal to the client for Card 1 promotion in §5.10; stripped before the prompt).
   - **Direct's homepage** (Direct only, when `homepage_delta` is not set): over Direct's `channel_pages` rows whose path is the root or classified `HOMEPAGE`, `homepage_delta` = their summed change and `homepage_share_pct = round1(their current visits / max(Direct's current visits, Σ current visits of Direct's listed rows) × 100)` (0 when the change is 0).
   - **Device and visitor type** (each only when not set yet): sum `channel_breakdowns` per device and per segment (sanitized, canonicalized, placeholders skipped); pick the largest change in the channel's direction (ties: the smaller name) and keep it with its change when `|d| / |Δ| ≥ 0.10` (no upper cap; oversized rows are used only as an empty-card fallback in §5.10). A device is also dropped when its share of the change is within 10 percentage points of its share of the channel's current visits in those rows (a 95%-mobile site sees about 95% of any change on mobile).
   - A value the request already carries on `traffic_channel_surges` is kept as given, without the band check; without its delta it produces no sub-row.
   - `channel_breakdowns` and `channel_pages` are then dropped.

#### Multilingual Content Safety Pre-filtering

Search queries, referrers, page titles and campaign names pass a deterministic screen (`internal/utils/sanitizer/sensitive.go`) before any card or prompt sees them. It normalizes first (Unicode NFKC, lower case, Latin diacritics, Arabic harakat, zero-width characters and soft hyphens removed; Cyrillic/Greek look-alikes and leetspeak mapped to Latin letters inside Latin tokens, a token written wholly in look-alike letters also read as Latin; repeated letters collapsed; spaced-out single letters joined), then matches a curated multilingual term set as whole tokens, stems or substrings: the x + video family in any spelling, spacing or order (`x vidio`, `xxx videos`, `video x`, `एक्स वीडियो`, `хх видео`, with Hinglish/Hindi filler words skipped between the two words), adult site names, `sex`/`porn`/`nude`/`chudai`/`chod*`/`chut`/`lund`/`bf video`/`blue film`, Arabic `سكس`/`نيك`/`طيز`/`جنس` with a film or picture word, Devanagari `सेक्स`/`चुदाई`/`चोद*`/`बीएफ`, and Bengali, Tamil, Telugu, Cyrillic, Chinese, Japanese, Korean, Thai and Indonesian equivalents. `chut` matches only without diacritics (the Vietnamese `chút` is kept) and `lund` is kept when it names the Swedish city or its university. A masked word (a letter followed by three or more `*`, `•` or `#`, or a one-letter word followed by two) is sensitive. It fails closed on the bare word ("sex education policy" is hidden).

#### Sources, Campaigns and Channel Routing

A `referrers` value is classified before it is labelled:

- **Dropped**: placeholders (`(not set)`, `unknown`, `(direct)`, `(unlinked SA360 account)` and similar); internal, staging, CDN, scanner and audit-tool hosts (`*.corp.google.com`, `art-analytics.appspot.com`, `tagassistant.google.com`, `*.internal`, sandbox and `dev.`/`stage.`/`staging.`/`test.`/`preview.` hosts, hosting and tunnel suffixes such as `*.instawp.*`, `*.pantheonsite.io`, `*.ngrok.*`, `*.vercel.app`, `*.appspot.com`, `localhost`, CDNs such as `*.cloudfront.net`, `gstatic.com`, `*.storage.googleapis.com`, mail scanners such as `safelinks.protection.outlook.com`, and audit tools `lighthouse`, `pagespeed`, `gtmetrix`, `webpagetest`, `screamingfrog`, `semrush`, `ahrefs`); sensitive values; search engines when the request has an Organic Search channel.
- **Search engines**: bare GA4 names and apex hosts (`google`, `bing`, `yahoo`, `yahoo.com`, `baidu`, `duckduckgo`, `ecosia`, `yandex`, `naver`, `seznam`, `qwant`, `startpage`, `ask`, `aol`), `google.<tld>` / `yandex.<tld>` (one or two labels of 2–3 letters, so `googleblog.com` does not match), `*.search.yahoo.com`, `*.bing.com`, `m.baidu.com`. Without an Organic Search channel they belong to Organic Search, never to Referral, and they are never ranked as sources.
- **Campaign**: no hostname suffix (a trailing `.` plus two or more letters) and either an underscore anywhere or a hyphen-separated token that is a year (`19xx`/`20xx`). Labelled for readers (`Newsletter_October_2025` → `October 2025 newsletter`; other shapes only have `_` and `-` replaced by spaces) and screened again for sensitive content.
- **Domain** (everything else), canonicalized: `wmx` → `Google Search Console`; Facebook variants (`fb`, `facebook`, any `facebook.com` host) → `Facebook`; Instagram, LinkedIn (`lnkd.in`), X (`t.co`, `twitter`), Reddit, YouTube (`youtu.be`) and Pinterest (`pin.it`) to their apex domain; ChatGPT, Perplexity, Copilot, Gemini and Claude to their product domain; the three Microsoft Teams hosts → `Microsoft Teams`. Sources with the same canonical name are summed.
- **Channel of a source**: search engines → Organic Search; AI assistants → AI Assistant; social platforms (by name; `x.com` and `t.co` only exactly or as a subdomain) → Organic Social; mail providers and newsletter-shaped names → Email; anything else → Referral (Search Console included: its visits start in the Search Console UI, not on a results page). Substack belongs to both Referral and Email. A campaign belongs to Email when its name is mail-shaped and to no channel otherwise.
- **Channel names** use the GA4 / Site Kit labels (`Organic Search`, `Paid Other`, …), except the two opaque GA4 defaults are humanized to plain English: `Cross-network` → `Cross-network ads` and `Unassigned` → `Uncategorized traffic` (translated in non-English locales via each Tier 1 glossary or Tier 2 rules, like `Paid traffic`). Channels are matched case-insensitively with their plain-language aliases.

### 5.10 Key Factor Cards (`decomposition`)

#### Goals and requirements

1. **Answer the reader's question about the period in at most three cards.**
   - A period that moved (`UP`/`DOWN`: more than ±5% on visits) answers *"what caused this shift?"*: `CONCENTRATED` when the largest channel moving with the period carries at least half of the movement in the period's direction, `DIFFUSE` otherwise; both report movements.
   - A flat period whose channels moved against each other answers *"how is my traffic mix shifting?"* (`OFFSETTING`).
   - A flat period where nothing moved materially answers *"what holds my traffic up?"* (`STEADY`): the largest channels by share of site traffic, each headlined with its own signed change.
2. **Rooted in where visits came from.** Every visit has exactly one acquisition channel, so cards are drawn from the channel partition. A card names a channel, the paid group (`Paid traffic`, when two or more paid channels each carry at least 10% of the paid channels' gross movement), or a child of a channel (a landing page, a referring site, a campaign) that carried at least half of its channel's change with no sibling from the same breakdown reaching 25%. Search keywords, devices and visitor types are never cards, only sub-rows.
3. **Largest movement first.** At most one card moves against the period (`OFFSET`), except on an `OFFSETTING` period, which shows both sides: up to two cards from the side it leaned towards and one from the other, with any slot left free filled by the next largest movers of either side. A period that moved always has at least one card moving with it.
4. **Every number belongs to the name next to it.** A card's figure is the named entity's own; every sub-row carries its own figure; rows without a figure are never shown.
5. **Every percentage names its denominator** (`share_basis`).
6. **Size words need a site-level share.** Only a card carrying at least 25% of the site's gross movement (`is_large_share`) may be described with words such as "sharply" or "surge".
7. **The cards reconcile.** `opening_sessions + Σ delta + residual_delta = closing_sessions`; on a full channel export the opening and closing figures are the site's visit totals.
8. **Nothing unrecognisable or unsafe is shown.** The homepage, its aliases and junk pages never appear as a card or `Target page` (on Direct the homepage may appear as a `Homepage` row without an address); sensitive text and internal or personal campaign names never appear.
9. **What the reader sees is what the text describes.** The client renders the cards it sends; the endpoint narrates those cards, less any part it cannot use (*Endpoint screening* below), and returns none. A request without cards is still narrated from the totals and the contextual data.

#### Design

Compute on the prepared copy (§5.9). There are no cards when there are no channel rows (send no `decomposition`). All rounding is to one decimal, half away from zero (`round1(v) = round(v × 10) / 10`; IEEE `-0.0` is normalized to `0.0`; PHP `round($v, 1)` matches, JavaScript `Math.round` does not for negative values).

**Step 1: Direction.** `pct = round1((V_cur − V_prev) / V_prev × 100)` on `visits.current_period` / `visits.previous_period` (with `-0.0` normalized to `0.0`); `UP` when `pct > 5.0`, `DOWN` when `pct < −5.0`, else `STABLE` (`V_prev = 0`: `UP` when `V_cur > 0`, else `STABLE`). The period is *notable* when `UP` or `DOWN`. The endpoint uses the same rule, so the cards always follow the direction the narrative is written for.

**Step 2: Partition figures.**
- When the rows carry both a `Paid Traffic` total and paid sub-channels, drop the total.
- `opening, closing` = Σ channel visits (previous, current) when `Σ previous ≥ visits.previous_period` or both visit totals are 0; otherwise the visit totals (a partial channel export leaves the unreported traffic in the residual).
- `totalDelta = closing − opening`; `siteRate = totalDelta / opening` (0 when `opening = 0`); `denom = max(opening, closing)`, or 1 when not positive.
- Per channel: `Δ = cur − prev`; `excess = Δ − prev × siteRate`; `excessPct = |excess| / denom × 100`; `volShare = cur / closing × 100` (0 when `closing = 0`); `impactPct = Δ / denom × 100`.
- `scDelta = search_clicks.current − search_clicks.previous` and `scTotal = max(search_clicks.current, search_clicks.previous)` (both 0 without `search_clicks`).
- Row floor (K2): `minRow = round(10 × d / 28)` (at least 1), the same 28-day count as Gate A's absolute floor.
- **Paid group.** Paid channels: Paid Search, Cross-network (`Cross-network ads`), Paid Social, Paid Other, Paid Shopping, Paid Video, Display, Paid Audio (and a plain paid total). `grossPaid = Σ |Δ|` over them; a paid channel *qualifies* with `|Δ| ≥ minRow` and `|Δ| ≥ 0.10 × grossPaid`. When at least two qualify and their net `Σ Δ ≠ 0`, all paid channels in the card-node list (`cardNodes`) are replaced by one node titled `Paid traffic` (`cur = Σ cur`, `prev = Σ prev`, `Δ = Σ Δ`, `excess = Δ − Σ prev × siteRate`, ranked by `grossPaid`), placed after the other channels. Otherwise every paid channel stays a channel. `STEADY` always uses the ungrouped channels.
- Gross pools over `cardNodes` (after paid grouping, so a paid swap counts once as its net paid change rather than inflating the directional denominators): `up = Σ max(Δ, 0)`, `down = Σ |min(Δ, 0)|`, `totalGross = up + down`.

**Step 3: Primary direction.** Notable: the period's direction. Flat (`STABLE`): the sign of the largest card-node mover's `|Δ|` (`DOWN` on ties when `down > up`, else `UP`), so the largest mover is always `PRIMARY` (Card 1) and the opposing mover is `OFFSET`. Gate C can then show a smaller child on Card 1 (Referral +1,000 shown as substack.com +550 beside Direct −800): when an `OFFSET` card's shown `|delta|` exceeds Card 1's after Step 8, the primary direction is flipped and Steps 6–8 rerun, and the flipped cards are kept only when no `OFFSET` card exceeds their Card 1. A *counter-mover* moves against the primary direction.

**Step 4: Shape.** Flat: `OFFSETTING` when the largest `excessPct ≥ 1.0`, else `STEADY`. Notable: `CONCENTRATED` when the primary pool is positive and the largest `|Δ|` among card nodes that are not counter-movers is at least half of it, else `DIFFUSE`. The primary pool here is summed over the same card nodes (`Σ |Δ|` of the non-zero card nodes that are not counter-movers), so a netted paid group counts once, as its `Paid traffic` node. A `DIFFUSE` period whose cards (after Step 8) carry fewer than two `PRIMARY` cards is labelled `CONCENTRATED`, since the narrative names at least two `PRIMARY` cards on `DIFFUSE`.

**Step 5: `STEADY` cards.** Channels with `cur > 0`, sorted by `volShare` desc (differences up to 0.0001 tie, then `cur` desc), first 3. Each: `entity_kind CHANNEL`, `dimension TRAFFIC_CHANNELS`, `volume = cur`, `delta = Δ`, `excess = round1(excess)`, `direction STABLE`, `metric_type VOLUME_SHARE`, `share_basis VOLUME`, `traffic_impact_pct = round1(volShare)`, `role PRIMARY`, sub-rows from the channel's slots and fillers only (step 8c.2–3; no child rows), each measured against the channel's own `Δ`. `residual_delta = totalDelta − Σ delta`. Done.

**Step 6: Eligibility and ranking (and cross-channel dominant page Card 1).**
- **Cross-channel dominant page**: on a notable (`UP`/`DOWN`) period, before channel selection, check `cross_channel_pages` (§5.9) for a displayable landing page moving in the primary direction with `|delta| ≥ max(round(20 × d / 28), minRow)`, `|delta| ≥ 0.40 × primaryPool`, and at least 2 contributing channels each carrying `≥ 10%` of the page's change (with same-sign movement). If one qualifies, promote the largest such page to Card 1 (`entity_kind CONTENT`, `dimension PAGES`, titled from `PageTitles` or its path, `role PRIMARY`, up to 2 `CHANNEL` sub-rows carrying `share_of_parent_change_pct`, `DECOMPOSITION` from 25% else `CONTEXT`), subtract its per-channel visits from each contributing channel whose overlap is material (`|sub| ≥ 10%` of `|raw_ch_delta|` or `|sub| ≥ 10%` of `|page.Delta|`) so visits are never double-counted without turning unrelated tiny-overlap channels into `(other pages)`, rebuild `cardNodes`, gross pools, `totalGross`, and `CONCENTRATED`/`DIFFUSE` shape over the post-subtraction partition `{page.Delta} ∪ cardNodes` (so Card 1 and residual channel cards share one consistent denominator and PRIMARY shares never sum past 100%), mark those subtracted residual channels `"<Channel> (other pages)"` (skipping Gate C elevation and restricting sub-rows to other landing pages, plus `HOMEPAGE` alongside `TARGET_PAGE` on `Direct (other pages)` ordered by larger `|entity_delta|`), and select at most 2 remaining channel cards.
- A node is eligible when its rank size (`|Δ|`, or `grossPaid` for the paid group) is at least `max(round(10 × d / 28) (≥ 1), 0.005 × denom, 0.05 × totalGross)`. Sort by rank size desc, then `|excess|` desc (differences up to 0.0001 tie), then title.

**Step 7: Selection.**
- Not `OFFSETTING`: walk the ranking, skipping every counter-mover after the first, until 3 cards.
- `OFFSETTING`: walk the ranking taking at most 2 non-counter-movers and 1 counter-mover; then fill free slots from the untaken nodes in rank order, up to 3.
- Notable period with no selected non-counter-mover: add the node with the largest `|Δ|` moving with the period (the first in partition order on ties), dropping the last selected card when 3 are selected.
- Stable-sort non-counter-movers before counter-movers.

**Step 8: One card per selected node**, in order. Children elevated to a card are remembered across cards, so a child that dominates two channels is elevated only under the first.

- **a. Children of a channel**, each tagged with the breakdown (*slicing*) it was read from:
  1. *Landing page* (slicing: landing page): only when `Δ > 0` and the channel's reduced URL is displayable: the first `recent_content_momentum` entry with a displayable URL, a non-sensitive title, the same path and `sessions > 0`. Kind `CONTENT`, label `Target page`, title = its title (or the URL), `cur = sessions`, `prev = 0`, `delta = sessions`.
  2. *Search keywords* (Organic Search only; no slicing; clicks): every non-sensitive query whose clicks changed.
  3. *Session sources* (slicing: session source): every referrer that survives §5.9, moved (`Δ ≠ 0`) and belongs to this channel (§5.9 *Sources, Campaigns and Channel Routing*), kind `REFERRING_SITE` (label `Referring site`) or `CAMPAIGN` (label `Campaign`). Under AI Assistant the label is `Assistant` and the child never takes the card.
  4. *Campaigns* (slicing: campaign; Email, Organic Social, Paid Social and the paid channels): every `channel_campaigns` row of this channel that moved, titled for readers when the name is a single token (a name with spaces is kept as typed), dropped when the title is empty, sensitive, or already the title of a child from 1–3.
  Children with the same key are summed: the source family (`content:` + path, `query:`, `source:` for every session-source child, `campaign:` for a campaign-report child) plus the lower-case name. They are then sorted by `|delta|` desc, key asc. Rows of one slicing are disjoint parts of the channel; two slicings are overlapping cuts of the same visits, so children are only compared with, and listed beside, children of their own slicing.
- **b. Elevation.** Over the visit-counted children (keywords never take part): `topSame` = the first child moving with the channel, `topOpposite` = the first moving against it, `R = |topSame.delta| / |Δ|`. `topOpposite` counts as the other side of a net only when it clears the row floors (`|d| ≥ minRow` and `|d| ≥ 0.10 × |Δ|`, K2); a smaller one (Facebook −33 inside Organic Social +1,203) is ignored, as if it were not measured. The channel is a *net* when `R > 1` and either a counted `topOpposite` exists or `R > 1.10`; otherwise `R` is capped at 1. `topSame` takes the card when it exists, the channel is not a net, it is not an assistant, `R ≥ 0.50`, it was not elevated already, and no other child **of its slicing** moving with the channel has `|delta| ≥ 0.25 × |Δ|` — except when the block has only one card (`totalCards == 1`, i.e. no promoted cross-channel Card 1 and `len(selected) == 1`) and the elevated card would carry 0 sub-rows (`len(elevated.Attributes) == 0`), in which case Gate C is skipped so the parent channel keeps the card with its sub-rows. The card: the child's dimension, kind and title; `volume = cur`, `delta` = the child's change, `excess = round1(delta − prev × siteRate)`, `outsized` from those (8e); `direction` and `role` from the channel; `share_basis PARENT_CHANNEL`, `traffic_impact_pct = round1(R × 100)`, `parent_channel` = the channel's title, `parent_channel_delta = Δ`. When the uncapped `R` was above 1 (within the 1.10 slack) the card takes the moving-card share of 8d on its own change (`impactPct = delta / denom × 100`) while keeping `parent_channel` and `parent_channel_delta` so the parent channel remains visible on the elevated card — unless that fallback would land on `ShareBasisSiteTraffic` (`|child| > pool`), in which case Gate C elevation is skipped so the parent channel keeps the card and the child renders as an oversized sub-row. An elevated card has no sub-rows (other than a pigeonhole `TARGET_PAGE` when qualified); what the channel moved beyond the child falls into `residual_delta`.
- **c. Channel card sub-rows**, in priority order, keeping the first 2 that pass the consistency rule below:
  1. *Child rows.* A net channel lists `topSame` as a `CONTEXT` row with its own figure and share 0 (an *oversized* row, below) when `|topSame.delta| ≥ minRow`, followed by the counted `topOpposite` (8b) as a `CONTEXT` row with its own figure and share 0: the two sides of a *net pair*. When `topOpposite` is absent or below the row floors, only `topSame` is listed (oi.ie 2026-10-02: Referral +39 lists `aocr.org (+49)`, and `mebounds.com (−5)` is dropped). A net channel lists no other child row (no keyword row either). A channel that is not a net, on every channel except Direct, lists:
     - Organic Search's keyword row: takes the largest non-sensitive keyword (including brand/domain queries) moving with the channel (or matching `scDelta`'s sign when `scDelta` moves with the channel). It is named when `|d| ≥ minRow` and `|d| ≥ 0.005 × scTotal` (`0.5%` of `max(search_clicks.current, search_clicks.previous)`, falling back to `|d| ≥ 0.10 × |Δ|` only when `search_clicks` is absent). When `scDelta` has the opposite sign or `|d| > |scDelta|`, `oversized_query: true` is set so rendering uses plain English (`while other queries rose/fell`) instead of a misleading share. Row: kind `SOURCE_TYPE`, label `Search keyword`, `CONTEXT`, `entity_delta` in clicks, `share_of_search_clicks_pct = min(100, round1(|d| / scTotal × 100))` (omitted below 0.05%).
     - Up to 2 visit-counted children that are not landing pages, move with the channel, carry `|d| / |Δ| ≥ 0.10` and `|d| ≥ minRow` and were not elevated elsewhere, all from the slicing of the largest of them, largest first. A child with `|d| > |Δ|` (possible only within the 1.10 slack, since a larger one makes the channel a net) is an oversized row; the others carry their share (`DECOMPOSITION` from 25%, `CONTEXT` from 10% to 24.9%).
  2. *Slots*: Direct: `HOMEPAGE`, `TARGET_PAGE`, `VISITOR_TYPE` (when both `HOMEPAGE` and `TARGET_PAGE` qualify on Direct, the larger `|entity_delta|` is ordered first); every other channel: `TARGET_PAGE`.
  3. *Fillers*: Direct: `READER_DEVICE`; every other channel: `READER_DEVICE`, `VISITOR_TYPE`.
  A slot or filler is skipped when a row of its kind is already listed (child rows may share a kind: a keyword row and a referring-site row are both `SOURCE_TYPE`). A `TARGET_PAGE` row needs a non-zero change moving with the channel, a displayable URL, `|e| ≥ minRow`, and `|e| ≥ 0.10 × |Δ|` (25% remains the threshold for `DECOMPOSITION` vs `CONTEXT`); a device or visitor-type row needs `|e| ≥ minRow`, `|e| ≥ 0.10 × |Δ|`, and `|e| ≤ |Δ|` (an oversized device or visitor-type with `|e| > |Δ|` is emitted as an oversized `CONTEXT` fallback **only** when the card would otherwise have 0 attributes), while a `TARGET_PAGE` with `|e| > |Δ|` is an oversized row. The `HOMEPAGE` row needs `homepage_delta` moving with Direct, `|homepage_delta| ≥ minRow`, and `|homepage_delta| / |Δ| ≥ 0.10` (no excess-share gate); it has label `Homepage` and no text, and is an oversized row when `|homepage_delta| > |Δ|` (oi.ie 2025-08-01: `Homepage (+61)` under Direct +57). Every measured row no larger than its card carries `share_of_parent_change_pct = round1(|e| / |Δ| × 100)` and is `DECOMPOSITION` from 25%, `CONTEXT` below. An **oversized row** is a page (`HOMEPAGE`, `TARGET_PAGE`), one of the channel's own children (`Referring site`, `Campaign`, `Assistant`), or an empty-card fallback `VISITOR_TYPE`/`READER_DEVICE` with `|e| > |Δ|` moving with the card: it is `CONTEXT` with its own figure and share 0, never a share above 100% and never "all of the change", and the cards text explains it in plain English (`while other pages/campaigns/sources/devices rose/fell` or `while returning/new rose/fell`, Rendering). A landing-page child is named by its URL. Rows are never re-sorted by share (except the Direct `HOMEPAGE` vs `TARGET_PAGE` comparison): the priority both picks and orders them.
  4. *Consistency (K1).* No row carries a share above 100%. The only rows larger than their card are oversized rows, which carry no share: the larger side of a net pair, a page or child that moved further than its channel because the channel's other parts moved the other way (search_central 2026-05-04: one blog post +48,876 under Direct +45,260), or an empty-card fallback device/visitor-type row. The candidates are then walked in order and a row is kept only when it agrees with the rows kept before it:
     - (a) a keyword row (clicks, not part of the card's visits) is always kept;
     - (b) when the first two visits rows are a net pair (both share 0, opposite signs), they are the card's only visits rows and are kept or dropped together, never one without the other, even when they come from two cuts (a landing page and a referring site: neither carries a share, so nothing is counted twice);
     - (c) otherwise every visits row must come from the same *cut* of the card's visits as the first kept one, where the cuts are landing page (`HOMEPAGE`, `TARGET_PAGE`), the channel's own children (`Referring site`, `Campaign`, `Assistant`), `VISITOR_TYPE` and `READER_DEVICE`, because rows of two cuts overlap by an unknown amount — with one exception: when line 1 is an entity child (`Referring site`, `Campaign`, `Assistant`) and slot 2 is still free, a single `TARGET_PAGE` row may appear on line 2 with `share_of_parent_change_pct = 0` and role `CONTEXT` (so overlapping cuts never imply additive shares);
     - (d) after the first, a visits row is kept while the kept rows' `Σ |e| ≤ |Δ|`, so a card's shares never add past 100% (Homepage 92.2% and a page 49.4% of Direct: only the homepage is listed). One exception: when two same-slicing entity child rows (`Referring site`, `Campaign`, `Assistant`) each account for at least 30% of `|Δ|` and neither individually exceeds `|Δ|`, both are kept even if `|e1| + |e2| > |Δ|` (because an offsetting dip elsewhere in the channel pushed their sum past 100%, e.g. `x.com` +53.6% and `linkedin.com` +47.1% under Organic Social); both rows clear `share_of_parent_change_pct` to 0 and take role `CONTEXT` so shares never sum past 100%. An oversized row can therefore only be the first visits row, and it fills the card on its own.

     The cut is fixed by the priority order of 8c.1–3, not by the largest row. The first 2 rows that survive are the card's rows.
- **d. Card share.** On a flat (`OFFSETTING`, `!isNotable`) period, non-elevated cards carry no `share_basis` (`""`) and `traffic_impact_pct = 0` (rendered as plain visit deltas without `% of growing/decreasing traffic` or `offsetting part of the drop/rise`, since the site did not move notably). On a notable period: `OFFSET` card: `share_basis NET_CHANGE`, `traffic_impact_pct = round1(|delta| / |totalDelta| × 100)` when `totalDelta ≠ 0` and the result is below 99.5, else 0. `PRIMARY` card: take the gross pools (summed over `cardNodes`), zeroing the pool in the site's own direction when `totalDelta ≠ 0` and that pool is below `0.25 × |totalDelta|`; with a positive pool in the card's direction and `round1(|delta| / pool × 100) ≤ 100`, that is the share on `GROSS_CHANGE`; otherwise `SITE_TRAFFIC` with `round1(impactPct)` (signed).
- **e. Common fields.** A moving card has `metric_type DELTA`, `direction` from the sign of its `delta`, `role OFFSET` for a counter-mover and `PRIMARY` otherwise. `outsized` is true when `delta` and `excess` are non-zero with the same sign, `|excess| / denom × 100 ≥ 1.0` and `|excess| ≥ 0.5 × |delta|` (a diagnostic, never shown or ranked on).
- **Paid group card.** `entity_kind CHANNEL_GROUP`, title `Paid traffic`, `volume = cur`, `delta = Δ` (the net), share and role as above. Rows: the qualifying members (`|member Δ| ≥ minRow` and `|member Δ| ≥ 0.10 × grossPaid`) by `|Δ|` desc (ties: title), at most 3, each `kind CHANNEL`, `DECOMPOSITION`, label `Channel`, text = member title, `entity_delta` = its signed change, `share_of_group_gross_pct = round1(|member Δ| / grossPaid × 100)`; a member's `campaign` / `campaign_delta` is its largest campaign (as in 8a.4) moving with it with `0.25 ≤ |c| / |member Δ| ≤ 1` and `|c| ≥ minRow`. The member rows themselves are shares of the group's gross movement, not of its net, and are exempt from the consistency rule of 8c.4 (a group always lists at least two members).

**Step 9: Order, size flag and residual.** Stable-sort `PRIMARY` before `OFFSET`, then by `|delta|` desc (re-ranking on the figure each card shows, which on an elevated card is smaller than its channel's). `is_large_share = totalGross > 0 and |delta| ≥ 0.25 × totalGross` on every moving card (a paid group is judged on its net, so a near-cancelling swap ranks high but is never large). `residual_delta = totalDelta − Σ delta`.

#### Endpoint screening

The plugin owns the card algorithm and its constants; the endpoint keeps or ignores what it receives and never tunes, recomputes, re-selects or corrects it (`ChangeDecomposition.usable` in `internal/ai/key_factors_screen.go`, run by `BuildBenchmarkingPrompt` after the request is sanitized and its pages classified). It never rejects a request over its `decomposition`: it ignores the smallest unit that is wrong (a field, then a row, then a card), cleans text with its own sanitizing, never adjusts a number, and logs each ignored or rewritten item, with the field path and the reason but never the client's text, in the `benchmarking_inputs_ignored` warning (§4). Ignoring part of the decomposition affects only the narrative (mainly `driver`): the plugin still renders its own cards. The prompt, and the recorded payload (`prompt_payload`), carry the screened copy, so text the screens leave out is neither narrated nor stored.

| Received | Endpoint action | Narrative effect |
| :--- | :--- | :--- |
| Valid, safe | Keep as sent | Narrated as sent |
| An unknown `shape`, `metric_type`, card or row `role`, or a row `label` outside its kind's set (`TARGET_PAGE`: `Target page`; `HOMEPAGE`: `Homepage`; `SOURCE_TYPE`: `Search keyword`, `Referring site`, `Campaign`, `Assistant`; `CHANNEL`: `Channel`; `READER_DEVICE`: `Reader device`; `VISITOR_TYPE`: `Visitor type`); a non-finite `excess` | Ignore that field; the card or row stays | Narrated without that field |
| A percentage whose `share_basis` is missing, unknown or inconsistent: non-finite; outside `[0, 100]` (`[-100, 100]` on `SITE_TRAFFIC`; `[0, 100)` on `NET_CHANGE`); `NET_CHANGE` on a card that is not `OFFSET`; `VOLUME` on a card that is not `STABLE`; `PARENT_CHANNEL` without a usable `parent_channel` | Ignore the percentage, its basis and the parent fields; keep the card's own `delta` and `volume` | Named with its visits change, without a share |
| `parent_channel` / `parent_channel_delta` on another basis | Kept on elevated cards (`CONTENT`, `REFERRING_SITE`, `CAMPAIGN`) with `parent_channel` sanitized; ignored on channel and channel-group cards | Keeps the parent channel visible on slight-overrun elevated cards |
| A row share outside `[0, 100]`; `share_of_parent_change_pct` on a `Search keyword` row or a `CHANNEL` row on `CHANNEL_GROUP`; `share_of_search_clicks_pct` off a `Search keyword` row; `share_of_group_gross_pct` off a `CHANNEL_GROUP`'s `CHANNEL` row; text on a `HOMEPAGE` row | Ignore that field; the row stays | Narrated without it |

| `residual_delta` that does not reconcile (`closing_sessions − opening_sessions − Σ delta` over the cards kept), or negative `opening_sessions` / `closing_sessions` | Ignore `residual_delta` (and the negative totals) | None: the residual is never narrated |
| More than 3 cards, or more rows than the layout allows (2; 3 on `CHANNEL_GROUP`) | Ignore the excess beyond the client's first N | Only the first N are narrated |
| A card that cannot be narrated: unknown `dimension` or `entity_kind`; negative `volume`; a `direction` unknown or contradicting `delta` (`UP` ⇔ `> 0`, `DOWN` ⇔ `< 0`, `STABLE` ⇔ `= 0`, except `STABLE` on `VOLUME` whatever `delta` is) | Ignore the card (two fields that contradict each other are both unusable; the endpoint does not pick one) | The driver does not name it |
| A row that cannot be narrated: unknown `kind`; `entity_delta` 0; a `CHANNEL` row off a `CHANNEL_GROUP` or `CONTENT` card, or a non-`CHANNEL` row on `CHANNEL_GROUP`; a `Search keyword` row marked `DECOMPOSITION` (its clicks are not a part of the card's visits); a `SOURCE_TYPE` row whose `label` is missing or outside its set (the label decides whether its text is screened as a host, a campaign or a name) | Ignore the row | The driver does not name it |
| Text (card title, `parent_channel`, row text, `TARGET_PAGE` `value.title`, campaign) | Clean it: plain text already clean is kept, other plain text goes through `sanitizer.Sanitize`, a page address (a path, or an `http(s)` URL) or a host (a referring site, an assistant) through `sanitizer.SanitizeURL`, which drops its query string, fragment and credentials. Then screen it as contextual rows are screened (§7.2): not empty, at most 2,048 bytes, no `**` left by URL sanitizing, not a placeholder (`(not set)`…), `IsSensitiveContent` on names, no marker the output safety check rejects (`hasOutputBlockedMarker`: `javascript:`, `system:`, `you are now`… in `internal/ai/validator.go`; the model quotes names verbatim, so such a name would fail every attempt), also `IsOpaqueOrPersonalLabel` on campaigns and `isDevOrStagingOrCDNDomain` on hosts, and `isDisplayablePage` (never the root, nor a page the request's verdicts hide) on target pages and content cards titled by their address (a host written with a scheme, such as `https://chatgpt.com/`, is not a page and is not held to it). ## 6. Response Schema

### 6.1 Synchronous (`async` absent or false)

HTTP 200, for the request of §4.4 (illustrative model text; 1,250 visits sit 13% above the range's 1,110, and last year's +22% move exceeds the band's relative width of about 4%, so `repeat_last_year` holds and the analysis ends with the last-year clause):

```json
{
  "interaction_id": "01J7N3M5G8R2QW4T9V0XYZ1234",
  "model_version": "gemini-3.8-flash",
  "scenario": "ABOVE_EXPECTED.UP",
  "analysis": "Your traffic over the last 28 days is about 13% higher than usual for your site, and traffic also rose at this time last year.",
  "driver": "Visits rose 25.0% (+250 visits) compared to the previous 28 days, led by **news.example** (+220 visits, 73.3% of Referral's +300 visits), partly offset by **Direct** (-50 visits)."
}
```

| Field | Type | Meaning |
| :--- | :--- | :--- |
| `interaction_id` | string (ULID) | Identifies the recorded interaction; echoed by the feedback endpoint ([`ai_data_collection_and_quota_design.md`](ai_data_collection_and_quota_design.md#interaction-recording)) |
| `model_version` | string | Model that wrote the insight |
| `scenario` | string | The label the endpoint derived (§7.5): `<status>.<direction>`, today one of the 12 combinations of `ABOVE_EXPECTED`, `WITHIN_EXPECTED`, `BELOW_EXPECTED`, `NO_RANGE` with `UP`, `DOWN`, `STABLE` (e.g. `ABOVE_EXPECTED.DOWN`). An open value set: a client must handle a value it does not recognise (show the texts as they are) |
| `analysis` | string | The analysis in the requested locale: the period opening, the range status phrase, optional in-period spike clause and, when `repeat_last_year`, the last-year clause |
| `driver` | string | The change against the previous `d` days and what carried it, in the requested locale; entity names in `**bold**` Markdown |

Every field is omitted when empty; `operation_id` appears only on the asynchronous creation response (§6.2). The response carries no cards. A client must ignore fields it does not know. A successful response is cached for 24 hours, keyed by site, user, end date, locale, the deployed build and the body fields `end_date`, `days_in_period`, `visits` (`last_year` included), `contextual_data`, `baseline`, `history_days` and `decomposition`, as left after the optional inputs are screened (§4): a client `category_resonance` is dropped before the key is computed, while the contextual text and the `decomposition` are hashed as sent, since their sanitizing and screening run in the prompt build, after the cache lookup (screening the decomposition needs the page verdicts). Payloads that differ only in text the screens would rewrite therefore miss each other's entries, which costs a generation but never serves a wrong hit. The build is App Engine's `GAE_VERSION` (`"dev"` when unset), which every `make prod` deploy of the default service sets anew: `/v1` versions the wire contract, while the content changes with every prompt, glossary, model or post-processing change, so a deploy starts with an empty cache and never serves an earlier build's output (each active user regenerates once; during a traffic migration the two versions keep separate caches; an admin-only deploy leaves the default service's cache alone). A repeated request returns the cached body as it was stored (with its original `interaction_id`), before the rate limit is checked, so it consumes no quota and makes no model call; it records only a cache-hit marker row that points at the original interaction ([`ai_data_collection_and_quota_design.md`](ai_data_collection_and_quota_design.md#recording-lifecycle)). A request identical to one still generating does not generate again either: it gets 409 `generation in progress` (§6.3) and its retry finds the cached body, or, when both requests are asynchronous, the operation of §6.2 already running (§7.1).

### 6.2 Asynchronous (`"async": true`)

On a cache hit the cached body of §6.1 is returned at once, as for a synchronous request (no `operation_id`). When an identical asynchronous request is already generating and its operation has started, that operation is returned, with its own `operation_id`, `interaction_id` and `model_version`, without consuming the rate limit (§7.1). Otherwise the rate limit is consumed and the endpoint returns HTTP 200:

```json
{"operation_id": "Zk3Qm8…", "interaction_id": "01J7N3M5G8R2QW4T9V0XYZ1234", "model_version": "gemini-3.8-flash"}
```

The generation then runs in the background, bounded by 60 seconds, and caches its result as a synchronous one would. The creation response, like the operation returned to an identical request, carries `Retry-After: 2`: the recommended wait, in seconds, before the first poll.

**Known limitation.** The background generation is a goroutine on the server instance that took the request, so it does not survive the instance. An instance that shuts down normally interrupts it first: within about a second, the operation is saved as `FAILED` with `{"code": 503, "message": "operation interrupted", "status": "SERVICE_BUSY"}`. An instance that crashes takes the generation along and leaves the operation `RUNNING`; a poll made 95 seconds or more after the operation was created (`lro.StaleAfter`) then reads it as that same `FAILED` with code 503, since its worker can no longer finish it, and logs a warning with `event: ai_operation_abandoned`. Memcache can also evict a record while it is polled, which answers 404. **Client contract:** poll every `Retry-After` seconds until `done: true`; on `FAILED` with code 503, or on 404 for an operation created less than an hour ago, send the original request again, which costs nothing if the generation had cached its response first; stop polling after 2 minutes and treat the operation as interrupted. [`ai_async_operations_design.md`](ai_async_operations_design.md) designs the rest of the fix.

**Polling:** `GET /v1/ai/operations/{operation_id}?site_id=<site_id>` with the same `Authorization` header. A poll authenticates with the bearer token alone and takes no `site_secret` (one that is sent is ignored): `site_id` identifies the site, and the token's user must be registered on it. Users are stored per site, so a user of another site is not found. A poll reads only an operation its token's user created: the operation records the hashed Google user ID of the user whose request started it, and the poll's user must match it. Errors, in check order: 403 `missing authorization` / `invalid authorization`; 400 `missing parameter: 'site_id'`; 400 `Unable to retrieve site connection. You may need to perform a plugin reset.` for an unknown site; 403 `invalid authentication token`; 403 `user not found` when the user is not on the site, a user of another site included (500 `unexpected error` when the user lookup itself fails), as in §4; 404 `operation not found` for an unknown operation, another site's or another user's, of the same site included, or one whose record has expired (it is kept for 1 hour after it was created and again for 1 hour after it finished). The controller also checks that the user record found is of that site, answering 403 `user does not belong to the site` otherwise, as defence in depth: the per-site lookup means no poll reaches it today. HTTP 200 returns the operation:

```json
{
  "name": "Zk3Qm8…", "site_id": "abc123", "done": true, "state": "SUCCEEDED",
  "response": {"interaction_id": "01J7…", "model_version": "gemini-3.8-flash", "scenario": "ABOVE_EXPECTED.UP", "analysis": "…", "driver": "…"},
  "created_at": "2026-10-15T10:00:00Z", "finished_at": "2026-10-15T10:00:03Z"
}
```

| Field | Meaning |
| :--- | :--- |
| `name` | The operation ID |
| `site_id` | The site the operation belongs to |
| `done` | `false` while running |
| `state` | `RUNNING`, then `SUCCEEDED` or `FAILED` |
| `response` | On success: the body of §6.1, as a JSON object |
| `error` | On failure: `{"code": 500, "message": "<the message of the §6.3 error the synchronous request would have returned>", "status": "<its §6.3 code>"}`; a timeout is a failure too. `status` carries the same machine-readable code the synchronous error body carries under `code` (e.g. `MODEL_OUTPUT_INVALID`, `MODEL_UNAVAILABLE`, `INTERNAL` for an error without a code of its own); clients match on it, never on `message`. A background generation that panics fails with `internal error` (`INTERNAL`), and the panic is logged; only that operation fails. One that an instance shutdown interrupts, or that is still running 95 seconds after its creation because its instance died, fails with `{"code": 503, "message": "operation interrupted", "status": "SERVICE_BUSY"}`: send the original request again |
| `created_at`, `finished_at` | RFC 3339 timestamps; `finished_at` once done |

A poll of an operation that is not done carries `Retry-After: 2`, the recommended wait before the next poll; a done operation carries none.

**Poll authorization.** The site, token and membership checks run in full at most once every 5 minutes for the same credentials. Credentials (site ID and bearer token) that pass them are remembered in memcache for 5 minutes with the hashed Google user ID of the token's user (`PollAuthCache` in `internal/ai/lro`, key `ai_poll_user:<SHA-256 of both>`, so they are never stored in the clear), and later polls with the same credentials skip the site read, the token lookup with its People API fallback, and the membership read, and match the remembered user against the operation's creator. A failed check is never remembered. A change that revokes remembered credentials (a revoked or refreshed token, a user removed from the site) therefore reaches polling within 5 minutes, and until then their polls get the operation rather than the check's error. A memcache failure only costs the full check.

### 6.3 Errors

Every error is `{"error": "<message>", "code": "<code>"}`. The `code` is the contract: clients match on it, and the message text may change. The code set is open: a client must treat a code it does not know by its HTTP status. A route timeout (`request timed out`) is answered by the router and carries no code.

| Status | Code | When |
| :--- | :--- | :--- |
| 400 | `INVALID_ARGUMENT` | A body that cannot be read or parsed, a required-core failure of §4, a wrong `site_secret` on the request (polling takes none) |
| 400 | `NO_DATA` | Both period totals 0 (or no `visits` object): a normal state for a new site or a broken tag; nothing is generated |
| 400 | `SITE_NOT_FOUND` | An unknown or deleted site: the plugin may need a reset |
| 403 | `PERMISSION_DENIED` | Missing or non-`Bearer` authorization, a rejected token, a user not on the site, a user of another site included (`user not found`, on the request and on polling alike). Polling also defines `user does not belong to the site`, a defence-in-depth check that no poll reaches today (§6.2) |
| 404 | `NOT_FOUND` | `operation not found`, on polling only: the operation is unknown or expired, or another user created it (§6.2) |
| 409 | `GENERATION_IN_PROGRESS` | `generation in progress`, with `Retry-After: 5`: an identical request (same site, user, locale and cache key fields of §6.1) is generating and this one cannot join it, because it is synchronous or the other request's operation has not started (§7.1); neither a generation slot nor the rate limit was charged |
| 429 | `RATE_LIMITED` | `rate limit exceeded`: the user's token bucket is empty; `Retry-After: 60` |
| 429 | `DAILY_CAP` | `daily cap exceeded`: the site spent its daily allowance; `Retry-After` is the seconds until the next UTC day, when the site's daily counter starts afresh |
| 500 | `MODEL_UNAVAILABLE` | `failed to generate benchmarking insights from llm`, including the 35-second model deadline and throttling that outlasts the retries of §7.9 |
| 500 | `MODEL_OUTPUT_INVALID` | `failed to parse llm response` or `llm output security validation failed`: the model answered but its output could not be used, even after one regeneration (§7.7); the rate limit charge was given back for an unparsable output and kept for one that failed validation |
| 500 | `INTERNAL` | `failed to build benchmarking prompt`, `failed to start async operation`, `unexpected error` (the site user lookup failed), and other internal failures. The prompt and start failures give the rate limit charge back (§7.1) |
| 503 | `SERVICE_BUSY` | `service busy`, with `Retry-After: 5`: the server instance had no free generation slot within 1 second (§7.1); the rate limit was not charged. An asynchronous request also gets it when the instance is shutting down; its rate limit charge is then given back. `request timed out` (no code): the request ran past the route's 45 seconds (§7.1). The model deadlines end first, so this takes a stall outside the model calls |

## 7. Endpoint Processing

### 7.1 Pipeline

Body parsing (before the controller runs, so before authorization), authorization, the plugin release from `User-Agent` (§4), the required core (§4), screening the optional inputs (§4; a client `category_resonance` is dropped here), site and secret, site user, locale, cache (§6.1), a claim on the cache key for identical requests in flight, a generation slot, rate limit, then generation: classify the request's pages (§7.2) under a 4-second deadline; build the prompt, which screens the client's `decomposition` (§5.10, §7.6); call the model under a 35-second deadline, retrying transient failures (§7.9); validate the output, regenerating an unusable one once (§7.7); cache and return. Each generation is recorded with the sanitized and screened request, the scenario, the model output and the plugin release. Asynchronous generation works on a copy of the request state taken before the handler returns.

The route bounds a request at 45 seconds (`timeout=45s` on the controller's route annotation), more than the wait for a generation slot and the two deadlines together (`internal/controllers/ai/deadlines.go`, held to the annotation by a test), so a slow model ends a synchronous request with the 500 of §6.3 rather than the route's 503. An asynchronous generation runs under the 60-second bound of §6.2 instead.

**Identical requests in flight.** Requests with the same cache key (§6.1) make one model call between them, across server instances. After a cache miss a request claims its cache key with an add-if-absent memcache write, which only one of several concurrent writers wins (`InFlight` in `internal/ai/caching`, key `ai_inflight:<cache key>`), then looks the cache up again in case an identical request cached its response in between. A request that finds the key claimed takes no generation slot and no quota: an asynchronous request whose identical twin is asynchronous gets the twin's operation (§6.2) once that operation has started, and any other request gets the 409 `generation in progress` of §6.3 with `Retry-After: 5`, whose retry usually finds the cached body. A synchronous request gives its claim back when it returns, after caching its response. An asynchronous one hands its claim to the background generation, which records its operation on the claim and gives the claim back when it ends, interrupted by an instance shutdown included. A failed generation therefore leaves nothing behind, and the next identical request generates again. A claim that is never given back, such as one on a server instance that crashed mid-generation, lapses after 90 seconds (`caching.ClaimTTL`, which a test holds above the route's 45 seconds and above the slot wait plus the 60-second asynchronous bound). A memcache failure while claiming does not fail the request: it generates without a claim. Joining a twin and being turned away are logged at `INFO` with `event="ai_generation_in_flight"`, `feature` and `outcome` (`joined` or `refused`).

**Generation slots.** A server instance runs at most 100 generations at once, shared with conversion insights (`internal/ai/capacity`). A request that finds every slot taken waits up to 1 second for one, then gets the 503 `service busy` of §6.3 with `Retry-After: 5`. The slot is taken after the cache and the claim, so a cached answer or an identical request in flight needs none, and before the rate limit, so a refused request costs no quota. A synchronous request gives its slot back when it returns. An asynchronous one hands its slot to the background generation, which gives it back when it ends, so background generations count against the same limit. The endpoints are served by the default App Engine service, whose instance cap times the slots bounds the generations running at once (README, "AI Endpoints").

**Quota refunds.** The rate limit is charged before the generation runs and given back when the request gets nothing from the model. That covers an interaction ID that cannot be minted, an asynchronous operation that cannot be started (including on an instance that is shutting down), and a prompt that cannot be built. It also covers an error answer from Vertex AI to the main call (throttling, a server error or a rejected request) after the retries of §7.9, within the 35-second deadline, and a last output that is not JSON, even after the one regeneration of §7.7 (a failure on the server's side, so a retry costs the user nothing). The charge is kept when the main call runs out of time, the request is cancelled, an instance shutdown interrupts the generation, or the call gets no answer at all, since the model may have run and been billed. It is also kept when the last output parses but fails the schema or safety check: the request's own text can steer that output, so a refund would let it buy model calls for free. A regeneration's model call is refunded or kept by the same rules as the first call's. The page classification plays no part, since it never fails a request. An asynchronous generation refunds in the background, so a `FAILED` operation (§6.2) may or may not have cost a charge. The refund frees the site's daily slot on the day it was charged and returns the user's token; how, and how it is logged, is in [`ai_data_collection_and_quota_design.md`](ai_data_collection_and_quota_design.md#quota-refunds).

### 7.2 Page Classification and Sanitization

The endpoint classifies pages as in §5.8, sending unresolved pages to a small model (`gemini-3.5-flash-lite`, minimal thinking); if that fails or times out it logs a warning, and the pages it sent count as `CONTENT` for that request, while the rules' verdicts and the remembered ones below still apply. It then sanitizes and reduces its copy of the request (§5.9) for the prompt. These verdicts shape the prompt's contextual data, and screen the client's `decomposition` too: its target pages and content cards titled by their address are classified with the contextual pages, and one they hide is left out of the narrated cards (§5.10 *Endpoint screening*), while the plugin still renders its own card.

**Remembered verdicts.** The model's verdicts are shared by every server instance through memcache (`PageVerdicts` in `internal/ai/caching`, DI `ai_page_verdicts`), so a site's unresolved pages are put to the model about once a week rather than on every generation:

- The rules run first and their verdicts are never cached. Only a page they leave unresolved is looked up, so a request whose pages the rules settle makes no memcache call.
- A page is looked up under `ai_page_verdict:<SHA-256>` of the classification call's hash, the site ID, the page key and title, and `site_has_root_page` as the model is told it. Sites never share verdicts, and no path or title is stored in the clear.
- The classification call's hash covers the system instruction (the rules and the known examples), the prompt's framing, the response schema and the temperature, so changing any of them starts afresh. A change of classifier model alone reaches remembered pages within 7 days.
- Only pages without a remembered verdict are put to the model. Every verdict it gives, `CONTENT` included, is remembered for 7 days (`caching.PageVerdictTTL`). A page it leaves out counts as `CONTENT` for that request only and is put to it again next time.
- The verdicts are written once the model has answered, under 1 second of their own (`rememberTimeout` in `internal/ai/caching/page-verdicts.go`) rather than what is left of the classification's 4 seconds, so a call that answers near its deadline still has its verdicts remembered. The main model call waits for the writes. A failed call remembers nothing.
- A remembered value that is not one of the three classes is ignored. A memcache failure costs only the model call and is logged as warnings, at most two per request: one for the reads that failed and one for the writes.
- The offline harnesses (`evaluate`, `evaluate-sites`, `latency`) remember nothing, so every run classifies its pages afresh.

### 7.3 Category Resonance

**Requirements.** Tell whether one WordPress category accounts for several of the site's most visited pages and changed materially against the previous period, counted the same way everywhere, without asking the plugin to rank or count.

**Design.** From `top_pages`: normalize each URL to its path; skip the root and pages with `visits ≤ 0`; merge paths that differ only by a trailing slash (visits summed, categories united, the shorter path kept); sanitize category names and drop placeholders; sort by visits desc, path asc; keep the 10 most visited; count each category once per page; keep categories on at least 2 of those pages; sort by count desc, name asc; keep 3. When `previous_top_pages` is present on the request, derive the previous period's top-10 category counts the same way and record `previous_top_urls_count` on each entry (`0` when the category was not in the previous top 10). The result (`category_resonance: [{category_name, top_urls_count, previous_top_urls_count}]`) replaces `top_pages` and `previous_top_pages` (the prompt JSON carries only the entries that pass `isMaterialCategory`, below, with `previous_top_urls_count` stripped, so an unchanged category listed first is never read as the subject). Page classes are not applied. A category with `top_urls_count ≥ 3` and, when `previous_top_urls_count` is known, `|top_urls_count − previous_top_urls_count| ≥ 2` (`isMaterialCategory`, S2) is the `CATEGORY` subject (§7.5).

### 7.4 Trends

| Field | Rule |
| :--- | :--- |
| `current_period_traffic`, `current_period_traffic_pct` | §5.10 step 1. `current_period_traffic_pct` is omitted when `visits.previous_period` is 0: a rise from zero visits has no percentage. |
| `status_vs_baseline` | Always set. `visits.current_period` against the range: `ABOVE_EXPECTED` above `expected_range_max`, `BELOW_EXPECTED` below `expected_range_min`, else `WITHIN_EXPECTED` (bounds inside); `NO_RANGE` without a baseline. The range is a forecast from the days before the period, so the status is independent of the period's own direction. |
| `range_distance_pct` | Only `ABOVE_EXPECTED` / `BELOW_EXPECTED`: how far the total sits beyond the nearest bound, as a whole percentage of that bound, `round(100 × (visits − max) / max)` above and `round(100 × (min − visits) / min)` below, rounded half up in integer arithmetic. Always stated from 1% (there is no larger floor: "higher than usual" without a number reads the same as a large gap). Omitted below 1% (`range_distance_slight` instead) and on a zero bound, where no distance can be measured and the analysis uses the plain phrase. |
| `range_distance_slight` | `true` only for `ABOVE_EXPECTED` / `BELOW_EXPECTED` less than 1% beyond the nearest bound, on the exact ratio (`100 × beyond < bound`, so 0.99% is still slight): the analysis says "slightly" with no figure. Omitted otherwise, and on a zero bound. |
| `range_transition` | Derived on the endpoint from `visits.previous_period` against the current `baseline` bounds (no wire-schema change) when the previous period sat materially outside the expected range: `RETURNING_FROM_ABOVE` (`WITHIN_EXPECTED` + `DOWN` + `previous_period > max` by at least 10%, `RangeDistancePct ≥ 10`), `RETURNING_FROM_BELOW` (`WITHIN_EXPECTED` + `UP` + `previous_period < min` by at least 10%, `RangeDistancePct ≥ 10`), `DOWN_FROM_HIGHER` (`ABOVE_EXPECTED` + `DOWN` + `previous_period > current_period`), `UP_FROM_LOWER` (`BELOW_EXPECTED` + `UP` + `previous_period < current_period`). | `in_period_spike` | Copied from the request's `in_period_spike` (§4) when a 1–3 day run exceeded weekday-adjusted daily `ExpectedMax` (`BuildExpectedRangeSeries`, falling back to `ExpectedRangeMax / periodDays`), accounted for `≥ 40%` of a positive period delta, met either `DirectionUp` or `≥ 5%` of current-period volume, and on `ABOVE_EXPECTED` accounted for `≥ 40%` of `(current_period − ExpectedRangeMax)`; omitted otherwise. |
| `direct_surge_pattern` | Set when Direct is a `PRIMARY` surge (`Δ ≥ 200` period-scaled, `≥ 50%` of directional growth, `≥ 90%` new-visitor visits, and no `DECOMPOSITION` page or homepage sub-row): `"NO_LANDING_PAGE"` when explicit `not_set_landing_page_delta` (§5.9) is `≥ 50%` of Direct's delta; `"DISPERSED_PAGES"` when `has_channel_pages` is true, `(not set)` is `< 50%`, and neither `max_page_delta` nor `homepage_delta` reaches `5%` of Direct's delta. Omitted otherwise (including when `channel_pages` is absent). |
| `weeks_until_range` | Only `NO_RANGE` with `history_days` (§4.2): `⌈(d + 55 − history_days) / 7⌉` (`WeeksUntilRange`), the weeks until the period's first day has the 56 days of history its 28-day fit needs; omitted without `history_days` or once the history suffices. |
| `repeat_last_year` | `true` when last year moved the status's way by at least this year's relative band width (§5.5); omitted otherwise. |
| `subject` | `CATEGORY`, `RECENT_CONTENT` or `SEARCH_QUERY` when a contextual item is material enough to name in the analysis or driver (§7.5); omitted otherwise. |
| `ranked_impacts` | Channels (paid total dropped when sub-channels are present), sources and campaign-shaped sources (search engines excluded), visitor segments (a segment holding more than 75% of previous visits whose change is within 3 points of the site's is skipped when there are several), devices, and recent content (previous 0). Each: `delta`; `pct_change_self` (2 decimals; omitted with `is_new: true` when the previous figure is 0); `traffic_impact_pct = delta / visits.previous_period × 100` (current period when previous is 0; 2 decimals); `share_of_total_delta_pct`. Sorted by `|traffic_impact_pct|`, then `|delta|`; top 10. Search queries are never ranked. |
| `key_factors`, `opening_sessions`, `closing_sessions`, `residual_delta`, `shape`, `omit_lead_channel_delta` | Copied from `decomposition` (plus `omit_lead_channel_delta`, true when `shape == CONCENTRATED`, no material `OFFSET` card exists, and Card 1's channel delta — `Delta` on `CHANNEL`/`CHANNEL_GROUP`, `ParentChannelDelta` on elevated child cards — is within 95–105% of `siteDelta` with the same sign); absent without one. |

### 7.5 Scenario Label and Subject

The label is decided in code and returned in the response, never the model's echo: `<status_vs_baseline>.<current_period_traffic>` (`ScenarioLabel`), 12 labels in all (`ABOVE_EXPECTED`, `WITHIN_EXPECTED`, `BELOW_EXPECTED`, `NO_RANGE` × `UP`, `DOWN`, `STABLE`). It names the two answers the insight gives (§1) and nothing else: the range axis decides the analysis, the change axis the driver. The feedback endpoint accepts exactly these 12 values as `scenario_code`.

**Subject.** One contextual item may be selected (`subject` in the trends), checked in this order, the first that holds wins:

1. `CATEGORY` when a category satisfies `isMaterialCategory` (`top_urls_count ≥ 3` and, when `previous_top_urls_count` is known, `|top_urls_count − previous_top_urls_count| ≥ 2`, §7.3, S2);
2. `RECENT_CONTENT` when a recent post's visits are material;
3. `SEARCH_QUERY` when a query shift is material (below, S1 + S2).

**Materiality.** A signal counted in visits is material when `|count| ≥ max(round(50 × d / 28) (≥ 1), 0.01 × visits.current_period)`. `SEARCH_QUERY` needs all of (S1, S2): (a) the Organic Search channel's visit change is positive and material; (b) `search_clicks` grew (`siteClicks > 0`) and the site's visit direction is not `DOWN`; (c) some non-sensitive keyword (brand/domain queries included, merged case-insensitively) gained at least `max(round(50 × d / 28), 0.25 × siteClicks)` clicks (`clicks > 0`); and (d) when `decomposition` is present, that keyword appears as a `"Search keyword"` sub-row on a `PRIMARY` `Organic Search` card with `entity_delta > 0` and `share_of_search_clicks_pct ≥ 5.0`. Without `search_clicks` no query is the subject: the listed queries are a top-N cut and cannot be a denominator.

On the 242 real checkpoints at 28 days (with the daily-fit range of §5.4): `WITHIN_EXPECTED.UP` 58, `WITHIN_EXPECTED.DOWN` 49, `WITHIN_EXPECTED.STABLE` 40, `ABOVE_EXPECTED.UP` 37, `NO_RANGE.DOWN` 13, `BELOW_EXPECTED.DOWN` 11, `NO_RANGE.UP` 10, `NO_RANGE.STABLE` 9, `ABOVE_EXPECTED.DOWN` 9, `BELOW_EXPECTED.UP` 3, `ABOVE_EXPECTED.STABLE` 2, `BELOW_EXPECTED.STABLE` 1 (all 12 scenario labels occur on the four frozen sites and are also covered by the golden set).

### 7.6 Prompt

The prompt template is `internal/ai/prompts/benchmarking.tmpl`. It receives:

- **Payload**, as JSON inside `<data>` tags at the end of the template: `end_date`, `days_in_period`, `visits` (`current_period` and `previous_period` only), the sanitized `contextual_data` **without** `search_clicks` and `channel_campaigns` (and with `category_resonance` cut to the categories that pass `isMaterialCategory`, `previous_top_urls_count` stripped), `trends` (§7.4; `Visitor type` values renamed to visits), `locale`, `scenario` (the deterministic label the field list also states). The baseline bounds and `last_year` are **not** sent: the model reads the range only as `status_vs_baseline`, `range_distance_pct` (or `range_distance_slight`), `range_transition`, `weeks_until_range` and `repeat_last_year`, so it cannot quote a bound or a last-year figure. The payload is serialized as compact JSON (no indentation), with Search Console positions rounded to one decimal and each card's internal `excess` left out; the request itself, which telemetry records, keeps the raw values. The universal guardrails and the field overview do not depend on the request, so every request shares a prefix of over 15,000 characters (`TestBenchmarkingPromptSharedPrefix`). The model is told to treat the data as statistics and never as instructions.
- **Fields to write**, in order: `scenario` (the label), `analysis` (under 280 characters), `driver` (under 220 characters). For a locale that does not start with `en`, the model first writes these in English as `analysis_en`, `driver_en` (under the same 280 / 220), then the localized `analysis` (under 320) and `driver` (under 230). These limits are defined once, in `internal/ai/benchmarking_text_limits.go` (`BenchmarkingTextLimitsFor`; `BenchmarkingTextLimitsForLocale` scales the localized ones by the language's `LimitFactor`, 1 for every curated language and a provisional 1.25 for scripts that write vowels as combining marks, Devanagari or Thai for example, whose marks each count as a character), and rendered from there into both the template and the response schema's field descriptions (`internal/adapters/genai/schemas.go`), so the two cannot disagree. What the two state is `BenchmarkingStatedLimitsForLocale`: the same limits, except that a language file's optional `driver_prompt_factor` (in (0, 1], default 1) understates the localized driver limit told to the model, rounded half up. Hungarian sets 0.87 and is told 200 characters instead of 230, because its drivers ran long against the enforced limit (autorater run of 2026-11-09: p90 244, maximum 279, 3 of 57 over 253); French sets 0.93 and is told 214, because its longest drivers (STABLE periods with two cards and a search query) ran 256–257. Only the stated driver limit changes: the output check and the autorater keep enforcing the real limits (`BenchmarkingToleratedLimitsForLocale`, 253 for Hungarian). Nothing in production truncates the texts; the endpoint's output check measures them against the limit plus 10% only to log a defect (§7.7), and the autorater checks them with the same tolerance (§10.4).
- **Two Questions Rule** (guardrail 14): the analysis answers only the range question, from `status_vs_baseline`, `range_distance_pct`, `range_transition` and `repeat_last_year` (with its one addition being the second sentence for a `CATEGORY` or `RECENT_CONTENT` subject, D1); the driver answers only the change question, from the change axis. No period-over-period figure, direction or comparison in the analysis (except the fixed `range_transition` status wording in `analysis`, which carries no percentage or visit delta), no range status or last year in the driver, and the two are never reconciled with numbers.
- **Range wording** (W1): the analysis compares the period with what is usual for the site over the long term and describes a level, never a movement ("remained", "stayed", "steady", "stable", "rose", "fell", "grew", "dropped" are banned there; the driver keeps the movement verbs and never says "usual", "normal", "typical" or "expected"). The wording rotates between three variants so the insight does not say "usual" every week. `RangeVariantFor(end_date)` = ⌊days since 1970-01-01 / 7⌋ mod 3 picks it: the same period always gets the same variant, the seven days of a week share one (the dashboard can be opened on any day), and consecutive weekly checkpoints differ; an unreadable date gets variant A. The prompt builder, the judge (`EvaluateBenchmarking`) and `check-sites` all call it, so they agree on the phrase a period must carry. The phrases (the `range` section of `internal/ai/prompts/languages/en.yaml` and of each Tier 1 language file, §7.6.1, read through `RangeWordingFor` and `rangePhraseGlossary` in `internal/ai/prompt_builder_range.go`; analysis phrases after "…had N visits"):

  | Status | A ("usual") | B ("normal") | C ("typical") |
  | :--- | :--- | :--- | :--- |
  | `WITHIN_EXPECTED` | is in line with what's usual for your site | is normal for your site | is typical for your site |
  | `WITHIN_EXPECTED` (`RETURNING_FROM_ABOVE`) | is returning to what's usual for your site after an earlier spike | is returning to what's normal for your site after an earlier spike | is returning to what's typical for your site after an earlier spike |
  | `WITHIN_EXPECTED` (`RETURNING_FROM_BELOW`) | is returning to what's usual for your site after an earlier dip | is returning to what's normal for your site after an earlier dip | is returning to what's typical for your site after an earlier dip |
  | `ABOVE_EXPECTED` | is about X% / slightly / — higher than usual for your site [, though down from its recent peak] | is about X% / slightly / — higher than normal for your site [, though down from its recent peak] | is about X% / slightly / — above your site's typical level [, though down from its recent peak] |
  | `BELOW_EXPECTED` | is about X% / slightly / — lower than usual for your site [, though up from its recent low] | is about X% / slightly / — lower than normal for your site [, though up from its recent low] | is about X% / slightly / — below your site's typical level [, though up from its recent low] |
  | `NO_RANGE` | — we're still learning what's usual for your site [; check back in about N weeks] (every variant) | | |

  "about X%" is used with `range_distance_pct`, "slightly" with `range_distance_slight`, and the plain phrase ("—", no qualifier) when neither is set (a zero bound). Every glossary locale carries all three variants, the NO_RANGE phrase and the check-back clause (one and many weeks; the Slavic languages also the form for counts ending in 2–4 other than 12–14; Arabic also the dual `أسبوعين` for two weeks and `[N] أسبوعًا` for 11 and more, with `[N] أسابيع` for 3–10: `rangePhrases.checkBack`, `TestLocalCheckBack_ArabicPlurals`), but the prompt renders only the request's variant, and the check-back line only when `weeks_until_range` is set, with the count filled in. Every per-request range token sits after the request-independent instructions, so the cached shared prefix is the same for every variant (`TestBenchmarkingPromptSharedPrefix` covers all three, and `TestBenchmarkingPromptTemplate_RangeWordingAfterTheSharedPrefix` keeps guardrail 1 static).
- **Analysis**, built from a fixed formula: "Your traffic over the last `d` days" (no visit count in the opening, since the Traffic widget header already displays total visits) + the variant's status phrase (`RangeWording.StatusPhrase`: the "about X%" phrase with `range_distance_pct`, the "slightly" phrase with `range_distance_slight`, the plain phrase with neither, the `WITHIN_EXPECTED` phrase, or the `NO_RANGE` phrase followed by the check-back clause when `weeks_until_range` is set) + the last-year clause (`LastYearClause`: ", and traffic also rose at this time last year" / ", and traffic also fell at this time last year") exactly when `repeat_last_year`, plus a second sentence (Part 4, Subject Rule, D1) when `trends.subject` is `CATEGORY` ("**[Category]** had N of your 10 most visited pages.") or `RECENT_CONTENT` ("**[Article]** drew N visits since publication."). Nothing else: no visit total, no period-over-period figure, no direction word, no channel, referrer or search query, no month count. The Last-Year Clause Rule forbids any recurring or seasonal claim, any claim that the period is typical for the time of year, a similar size, a cause or a last-year figure. The English phrases and each glossary locale's wording are defined once, in the `range` sections of the language files (§7.6.1), read through `RangeWordingFor`, `rangePhraseGlossary` (`internal/ai/prompt_builder_range.go`) and `LastYearClause` (`internal/ai/prompt_builder.go`), and rendered into the glossaries.
- **Driver**: opens with the site's change against the previous `d` days ("Visits rose X% (+N visits) compared to the previous `d` days, …", "fell", or "were about the same as the previous `d` days (±X%, ±N visits), …", and "Visits were the same as the previous `d` days, …" with no figures when the two totals are equal, never "(0.0%, 0 visits)", "-0.0%" or "+0.0%"; "Visits rose to N (+N visits) compared to the previous `d` days, …" with no percentage when the previous period had no visits), the only place the site-wide change appears. When the driver continues after its opening, it uses "led by", "spread across", "while" or "with", never "as": after the opening, "as" reads as "because", and translations rendered it as a causal conjunction (Serbian "јер", Hindi "क्योंकि", Ukrainian "оскільки"), so neither the template, its examples nor the golden set's expected drivers write an opening (or the "..." the shape rules abbreviate it to) followed by ", as" (`TestBenchmarkingPromptTemplate_OpeningNeverContinuesWithAs`, `TestBenchmarkingGoldenSet_OpeningNeverContinuesWithAs`). Then the shape decides the sentence (`CONCENTRATED` credits the largest card, `OFFSETTING` names both sides, `DIFFUSE` names several together, `STEADY` the volume pillars, and only `STEADY`: a `STABLE` period with an `OFFSETTING` shape names the cards that moved with their own deltas); the largest `PRIMARY` card is always named with its own figure — except on `CONCENTRATED` when no `OFFSET` card is required and Card 1's delta is within 95–105% of the site delta in the same direction, where repeating the near-identical visit count is omitted ("led by **Organic Search**." instead of duplicating the opening figure); any `OFFSET` card with `share_basis: "NET_CHANGE"` and `traffic_impact_pct ≥ 25` is also named with its `delta` (`CONCENTRATED` and `DIFFUSE`; on `DIFFUSE` with such an `OFFSET` card, all three cards—Primary #1, Primary #2, and the `OFFSET` card—must be named), and the driver never repeats a `CATEGORY` or `RECENT_CONTENT` subject or opens with a standalone subject clause ahead of the cards (D1: when `trends.subject` is `SEARCH_QUERY`, the keyword is cited inside the `**Organic Search**` card clause from its `"Search keyword"` sub-row with its own clicks); when the largest `PRIMARY` card has a `DECOMPOSITION` sub-row with `share_of_parent_change_pct ≥ 40` (a target page, the homepage, a referring site or a campaign, never a visitor type or device), the driver names that sub-row with its `entity_delta` on every shape including `OFFSETTING` (D2, demonstrated in `BELOW_CONCENTRATED.txt` and `WITHIN.txt`); when a child's absolute change exceeds its parent's (`|child| > |parent|`, across elevated cards, paid groups, and sub-rows) and both figures appear in `driver`, `"mostly"` is banned and every stated overrun is reconciled — using `"while other [paid channels / campaigns / sources] rose/dipped"` (or naming the offsetting member on a paid group) for material gaps (`≥ 10` visits) and factually neutral `"while other traffic in **<Parent>** rose/dipped"` (translated in non-English locales) for smaller (`1–9`-visit) gaps so small export slack never invents competing campaigns or sources; when `trends.in_period_spike` is present, the driver notes the brief 1–3 day spike; when `trends.direct_surge_pattern` is present, the driver adds the matching neutral, non-speculative observation (`"NO_LANDING_PAGE"`: almost all first-time visits, mostly with no landing page recorded; `"DISPERSED_PAGES"`: almost all first-time visits, spread thinly across many pages with no single page standing out; never bots/spam/crawlers/tag audits); when a cross-channel `CONTENT` card is Card 1, its `CHANNEL` sub-rows may be cited as the channels bringing traffic to that page; the prompt ends the driver rules with a self-check that the required names are present (the largest `PRIMARY` card, plus the second card for `DIFFUSE`, the largest `OFFSET` card for `OFFSETTING`, and any `OFFSET` card with `share_basis: "NET_CHANGE"` and `traffic_impact_pct ≥ 25`), and when the length limit binds the model drops percentages, size words, paid member channels, volume pillars and `CONTEXT` rows before any of them; localized drivers translate "as"/"while" with correlative conjunctions, never causal ones ("da", "ya que"), and "led by" as composition ("dipimpin oleh"), never as a cause ("akibat"); an `OFFSET` card is cited in `driver` with its visit delta alone (`"partly offset by **[OFFSET]** ([delta] visits)"`, without stating a rounded `"offsetting about N%"` percentage in `driver`); an elevated card is named with its own figure, a `DECOMPOSITION` row may be cited as what led its card, a `CONTEXT` row only with its own figure; the paid group is "paid traffic" with its net figure, its members named as parts with their own figures when it is the largest card on `CONCENTRATED` or `OFFSETTING` and the length allows (on `DIFFUSE` alongside a second `PRIMARY` card, `"paid traffic"` is cited with its net figure alone so the second `PRIMARY` card is never dropped); a search keyword's share of search clicks is never signed; `"Visitor type"` and `"Reader device"` (`VISITOR_TYPE` and `READER_DEVICE`) sub-rows belong to the UI card details and `detailed_analysis` and are never cited in `driver`; "led by" appears at most once per sentence, so a campaign or sub-row under a card that already used "led by" is nested in the card's parentheses with "mostly"; campaign titles are used verbatim; Search Console figures stay clicks.
- **Universal guardrails**, numbered 0–14 at the top of the template, ahead of the field overview: 0 and 3 no SEO advice, ranking tactics or promised search outcomes; 1 no range numbers (no bound, no "baseline", "expected range" or "usual range"; `range_distance_pct` is the only range figure); 2 correlative framing; 4 empty contextual data (site totals only, no distribution claims, no tag audits); 5 the root URL and category hubs are never new content, and no invented titles; 6 Markdown bold on channels, domains, devices, queries and titles, with channel and category names kept untranslated; 7 figures preserved exactly, every localized field in its language's script, and no non-Latin script in Latin-script locales except a name the payload gives in another script, kept verbatim; 8 comparison windows (the driver compares with the immediately preceding period; the only statement about a year earlier is the last-year clause); 9 plain language, no buzzwords; 10 plain verbs; 11 visits unit; 12 plain wording (no scenario codes; "rose sharply" only with `is_large_share`); 13 size words only on `is_large_share` cards; 14 the Two Questions Rule. The **period length rule** ("N days", never a month or any other calendar unit) is the one rule that names the period, so it stands on its own just after the field overview.
- **Locale glossary** for the requested locale's language (none for English; §7.6.1), followed by the **language notes** (the generic translation rules of a language without a glossary, the regional idiom/vocabulary note of a non-default regional variant such as `en_GB`, `es_MX`, `es_AR` or `pt_PT`, the form of address of a `_formal` or `_informal` locale, the Swiss spelling of `de_CH`, and the number format of `es_MX`/`de_CH`), and **one example** from `internal/ai/prompts/examples/`, chosen by status and shape (`scenarioExampleName`): `SEARCH_QUERY` subject → `SEARCH_QUERY`; `ABOVE_EXPECTED` with `UP` → `ABOVE_CONCENTRATED` or, for a `DIFFUSE` shape, `ABOVE_DIFFUSE` (which carries `repeat_last_year`); `BELOW_EXPECTED` with `DOWN` → `BELOW_CONCENTRATED`; a status against the direction (`ABOVE_EXPECTED` not `UP`, `BELOW_EXPECTED` not `DOWN`) → `MIXED`; `WITHIN_EXPECTED` → `WITHIN`; `NO_RANGE` → `NO_RANGE`. Each example's cards are what the client computes for its data (`TestScenarioExamples_CardsMatchWhatTheClientSends`), and its analysis is the formula above (`TestScenarioExamples_TeachTheirOwnTrends`). The examples are templates over the period length and the range wording: their English and localized analyses are rendered in the request's variant (`renderScenarioExample`, from the glossary of the example's own locale), so no example teaches a variant the request does not use (`TestScenarioExamples_UseTheRequestsVariant`).

### 7.6.1 Locales and Languages

`hl` is resolved once, by `ai.ResolveLocale` (`internal/ai/locale.go`), and everything language-specific reads the resolved locale:

| Step | Rule |
| :-- | :-- |
| Normalize | `_` and `-` are alike, case is ignored, and WordPress variant suffixes that do not change the language are dropped (`ca_valencia`, `pt_PT_ao90`). A POSIX locale's encoding is dropped (`zh_TW.UTF-8` is `zh_TW`) and its `latin`/`cyrillic` modifier names the script (`sr_RS@latin`, `sr_RS_latin`). After a BCP-47 singleton (`-u-`, `-t-`, `-x-`) no subtag is read as a script or region (`de-u-co-phonebk` is `de`); only the register follows `-x-` |
| Glossary & tier lookup | By BCP-47 primary language (`ResolvedLocale.Code`), ISO 639-2/3 codes taking their two-letter form (`bel` is `be`) and deprecated codes their current one (`in` is `id`, `iw` is `he`, `mo` is `ro`); every English, Spanish, French or Portuguese variant looks up its language's tier and glossary (`en`, `es`, `fr`, `pt`). A locale that names no language (`art_xemoji`, malformed input) is English |
| Precise prompt locale | Non-default regions (`en_GB`, `en_AU`, `es_MX`, `es_AR`, `pt_PT`, `de_AT`, `fr_CA`, `de_CH`) stay on `ResolvedLocale.Region`, so `PromptLocale()` names the exact regional locale in the prompt and `localeVariantNote` instructs the model to tailor regional idioms, vocabulary, grammar and spelling where relevant (for example, `pt-PT` *"está a ser estabelecida"* / *"pesquisa"* / *"o seu site"* vs. `pt-BR` *"está sendo estabelecida"* / *"busca"*; `es-AR` Rioplatense phrasing and `.`/`,` separators vs. `es-MX` `,`/`.` separators) while keeping the required glossary or canonical phrases |
| Script | Kept when it differs from the language's CLDR likely script, given or implied by the region: `zh_TW` and `zh_HK` are `zh-Hant`, `zh_CN` and `zh_SG` `zh-Hans`, `sr_Latn` is `sr-Latn` |
| Spelling | `de_CH` and `de_LI` add an explicit Swiss Standard German note ("ss" instead of "ß") |
| Number format | A region whose CLDR decimal separator differs from its language's (`es_MX`, `es_419`, `de_CH` write `18.5` where `es` and `de` write `18,5`) gets an explicit number-format note (with a CLDR example) overriding the glossary's examples, and the number check reads the region's separators. A region that only groups differently (`de_AT`, `pt_PT`) uses its language's glossary separators |
| Register | `_formal` / `_informal` ask for the polite or familiar form of address in the prompt; the glossaries keep one register each |
| Cache key | `ResolvedLocale.CacheKey` (`de`, `de-x-formal`, `de-CH`, `en-GB`, `es-MX`, `es-AR`, `pt-PT`, `zh-Hant-TW`; `en` for default English `en`/`en_US`) replaces the raw `hl`, so default-region inputs share cached insights with their bare language (`de_DE` and `de` key as `de`; for a language without a glossary written in its usual script, the CLDR likely region is the default: `da_DK` and `da` key as `da`), while regional variants key separately (`de_AT` keys as `de-AT`). Interactions and recorded payloads keep the raw `hl` |

The **glossary entries** (the `glossary` section of each Tier 1 language file, loaded into `glossaryTable`, one `glossaryEntries` per Tier 1 language, rendered by one function, `glossaryEntries.render` in `internal/ai/glossary_entries.go`, in one order with one English key per line, the keys being the `canonical` phrases of `en.yaml`) are the same for every Tier 1 language, so no language falls back to English for a phrase another language's glossary translates: the analysis opening "Your traffic over the last `d` days" (ja-JP adds NEVER "前の`d`日間"); "compared to the previous `d` days" with the language's own year-over-year phrase marked NEVER ("im Vorjahresvergleich", "前年同期比", ...; never part of the allowed last-year clause); "visits" and "new-visitor visits" / "returning-visitor visits"; "as your average rank position improved"; "paid traffic" (fr-FR adds NEVER "trafic de paiement"), "Cross-network ads" and "Uncategorized traffic" (localized like "paid traffic" rather than kept as raw English labels); "led by" as composition; the banned cause wording (the language table's causal conjunctions plus the language's causative verbs, "due to" forms and cause nouns, e.g. "entraînant", "a causa di", "원인", "要因"; uk-UA allows "через" only in its time sense); the share wordings "of the growing traffic" / "of the gross gain", "of the traffic decrease", "offsetting about [X]% of the drop" / "of the rise" and "rose [X]%" / "grew [X]%" (ja-JP keeps its NEVER notes). The retired entries ("May", "increase in overall site traffic") are gone. The loader refuses a language file that leaves an entry empty, and `TestLocaleGlossary_EveryLanguageDefinesEverySharedEntry` fails when a Tier 1 glossary renders an entry empty, and `TestLocaleGlossary_NoStaleEntries` when a retired entry comes back. The template lists no per-language examples: the guardrails in the cached prefix (Correlative Framing Rule, Comparison Window Rule) are language-neutral and point to the glossary's banned words, and the per-request rules (Paid Traffic Group Rule, the localized driver) say "the glossary's \"paid traffic\", \"Cross-network ads\" and \"Uncategorized traffic\" wordings" and "the glossary's \"led by\"" (`TestBenchmarkingPromptTemplate_LanguageExamplesLiveInTheGlossary`); a Tier 2 prompt reads those as its own translation of the canonical phrase.

The **language table** (`languageTable`, loaded from the language files below; `languageOrder` in `internal/ai/language_table.go` lists the curated codes in the order every rendered list follows) is the single source of the language-specific data: tier, prompt tag (`de-DE` for every German locale; the glossary, golden entries and prompt name the language by it), script and direction, glossary vocabulary (the visits word, person words, "new-visitor visits", correlative conjunctions and causal words, which the Visits Unit Rule and the judge rubric list), English marker words that are also words of the language, the length factor (from the script, `scriptLimitFactor`) and the driver prompt factor (`driver_prompt_factor`, 1 unless the file sets it). Guardrail 7's list of Latin-script locales, the Visits Unit Rule's word lists and the judge's are rendered from it. A language without an entry gets a profile derived from CLDR (English name, likely script).

The **language data files** (`internal/ai/prompts/languages/<code>.yaml`, one per curated language, embedded with `go:embed` and loaded by `internal/ai/language_data.go`) hold all of this natural-language text, so a language fix is a data diff a linguist can review and the Go code keeps only the types, the loader and the prompt assembly. `en.yaml` holds the English range wording (every variant, the `NO_RANGE` phrases, the check-back clause and the last-year clauses) and the `canonical` English phrases: the English forms each glossary entry translates, which open its glossary line, and which the generic translation rules list. Each Tier 1 file holds the language's profile (`name`, `prompt_tag`, `alias_tags`, `script`, `rtl`, `english_marker_exclusions` and the optional `driver_prompt_factor`), its `vocabulary`, its `glossary`, its `range` phrases (the check-back clause as `check_back_one` for one week, with no figure, and otherwise the form of the week count's CLDR plural category, chosen with `golang.org/x/text/feature/plural`: the optional `check_back_one_counted`, `check_back_two`, `check_back_few` and `check_back_many` only where the language words that category differently, else `check_back_other`, so Russian reads "через 21 неделю", Czech "22 týdnů" and Arabic "100 أسبوع") and, for German, the `spelling_notes` of `de_CH` and `de_LI`. Every file but `en.yaml` is a Tier 1 language with a glossary. The files are read once at startup, strictly: a file that cannot be parsed, has an unknown or duplicate key, leaves a required phrase empty (every glossary text, every vocabulary list, every range phrase but the optional plural forms, every canonical phrase; a list with a blank element counts as empty), drops a glossary placeholder (`{days}` in the opening and comparison, `**[Name]**` in "led by", and `[X]` in the shares, offsets and self-growth), names a script `ScriptRanges` does not know (which would silently turn off the script checks and the length-limit factor), sets a `driver_prompt_factor` outside (0, 1] (it can only understate the stated driver limit), names a code other than its file name, reuses another file's prompt tag, or is missing or extra against `languageOrder` stops the binary, as a malformed prompt template does (`TestLoadLanguages_RejectsBadFiles`, `TestLoadLanguages_EmbeddedFilesAreCompleteAndCurated`). Moving the text out of Go changed no prompt byte: the prompt-hash snapshots (`internal/ai/testdata/benchmarking_prompt_hashes.csv`, `internal/ai/testdata/goldenset_prompt_hashes.csv`) are unchanged.

| :-- | :-- | :-- |
| English | `en`, all variants | English output schema |
| Tier 1, glossary | `de`, `es`, `fr`, `it`, `pt` (the `pt-BR` wording for every variant), `id`, `tr`, `ko`, `pl`, `ja`, `gl`, `uk`, `sr` (and `sr-Latn`, derived from `sr.yaml` by letter-for-letter transliteration, `serbianLatinFile`), `cs`, `ru`, `vi`, `nl`, `ar`, `hu`, `sv` | The language's glossary |

The **generic translation rules** (`tier2Instructions`, `internal/ai/prompt_language.go`) name the language and its script (and right-to-left direction), list every English canonical phrase the glossary would otherwise translate, from `en.yaml` in the request's range variant (`RangeVariantFor(end_date)`, the wording the template's English phrases use) (the seven status phrases including the two "slightly" ones, the `NO_RANGE` phrase, the two last-year clauses, "compared to the previous `d` days", the analysis opening "Your traffic over the last `d` days", and the check-back clause in its one-week and "[N] weeks" forms), keep names verbatim with their `**` markers except campaign titles, which carry neither `**` nor quotes (Campaign Attribution Rule), state the share wordings with their denominators, "led by" as composition and "paid traffic" as a translated description, and ask for one consistent, faithful translation of each, the visits word never a person word (for a language in `tier2VisitsWords`, the rule names both words: Thai writes "การเข้าชม", never "ผู้เข้าชม", which the autorater runs of 2026-11-09 caught; `TestTier2Instructions_NameAKnownVisitsWord`), correlatives never causal, and figures in Western digits with the language's CLDR separators (an example is rendered from CLDR). The model writes them in the same call as the `*_en` fields, so latency and cost are unchanged; the `*_en` fields stay fully checked. The digit policy is the same for every language: Guardrail 7 (Exact Number & Script Preservation) asks for Western digits (0-9) in every language, Tier 1 Arabic included, and the Tier 2 rules repeat it with the language's separators.

### 7.7 Model Call and Output

- **Model**: `gemini-3.8-flash` on Vertex AI (`global`), low thinking, default temperature, JSON output under a response schema, up to three attempts when a call fails transiently (§7.9). The production schema asks for `scenario`, `analysis` and `driver`, plus the two `*_en` fields for a locale that does not start with `en`; `detailed_analysis` is only requested by the offline `evaluate-sites` harness.
- **One call, bold repair and a defect log** (`BuiltPrompt.Generate`, `BuiltPrompt.RepairBold`, `BuiltPrompt.OutputDefects`): the model is called once, and an output with defects is never regenerated (only an unusable one is, below). A formatting-only repair then normalizes stray straight or curly double-quote characters placed inside a bolded name's `**…**` boundary (`repairBoldedQuotes`, e.g. `"**<Title>”**"` → `"**<Title>**"`, `"**<Title>”** (` → `"**<Title>**" (`, leaving internal quotes and titles that genuinely start/end with a quote untouched) and adds the missing `**` around the first plain occurrence of a card name (`trends.key_factors` card titles and channel/target-page/source-type sub-row names, never raw contextual queries or referrers) in `driver` and `driver_en` when the field never bolds it, skipping any match inside an already-open `**…**` span, continued by a combining mark (`\pM`), or joined to a longer hostname or path (preceded by `.`, or by `/` or `-` when the name is not a URL path; followed by `/`, `-`, or `.` and a letter or digit); the same repair adds the `**` around the subject's name (a resonant category or a newly published article of `trends.subject`, and nothing else) in `analysis` and `analysis_en`, where a translation sometimes drops the markers (quotes in id-ID, 「」 in ja-JP); the name must match whole, with its exact case, and nothing else is rewritten: the repaired strings are spliced back into the model's JSON, so key order, whitespace, the other fields and any text around the object (a code fence the lenient parse skips) keep their bytes. The markers count toward the length (the autorater counts them too), so names are added one at a time and a name whose markers would take a `driver` or `analysis` within its tolerated length past it is skipped (the names that fit stay bolded); a name the `driver`'s limit skips is skipped in `driver_en` too, so the repair never creates a `driver`/`driver_en` mismatch. The repaired output is what validation, the cache, the response and the `model_output` column receive, and the token and latency columns are that call's (both calls', summed, after a regeneration). After an output passes validation, code lists the defects it can see without a judge and logs them as a warning (`benchmarking output published with defects: …`); the output is published as it is. The defects are: an analysis or driver longer than its limit plus 10% (`BenchmarkingToleratedLimitsFor`, the same ceiling the autorater enforces); an English driver (`driver_en`, or `driver` in English) without, in bold, the names the self-check requires (the largest `PRIMARY` card, the second `PRIMARY` card for `DIFFUSE`, the largest `OFFSET` card for `OFFSETTING`, and any `OFFSET` card with `share_basis: "NET_CHANGE"` and `traffic_impact_pct ≥ 25`; only channel, page and referring-site cards, since "paid traffic" is translated and campaign titles carry no bold); a localized `driver` that drops a bolded name that `driver_en` carries and that translation keeps verbatim (card titles, member channels, landing pages, keywords and referrers from `trends.key_factors`); a localized `driver` that drops the own figure (the absolute `delta`) of one of those required cards that `driver_en` gives it (exempting Card 1 on `CONCENTRATED` when no `OFFSET` card is required and Card 1's delta is within 95–105% of the site delta in the same direction), read as whole numbers in any thousands separator (`93,511`, `93.511`, `93 511`, with a no-break, narrow no-break or thin space, a full-width comma or the Arabic thousands separator too), in Indian grouping (`1,93,511`) and in any decimal digit script (full-width, Arabic-Indic, Devanagari), so a locale without a glossary is not flagged for a figure it kept; corrupted nested bolding (`**…**…**`), stray double-quote characters inside bolded names (`HasStrayBoldedQuote`), repeated `"led by"` in a single sentence, `"led by"` or `", with … visits"` for `(new|returning)-visitor` in `driver`, or signed zero percentages (`-0.0%`, `+0.0%`, `(0.0%, 0 visits)`); and an analysis (or `analysis_en`) that carries a last-year clause the range status contradicts, in English or in the locale's glossary wording: the "fell" clause for `ABOVE_EXPECTED`, the "rose" clause for `BELOW_EXPECTED`, and either clause without `repeat_last_year`; and a localized `analysis` (any non-English locale, Tier 2 included) that keeps the English opening ("Your traffic over the last `d` days", "Over the last `d` days", or "your site had"), anywhere in the field (`untranslatedOpeningPattern`). An earlier version regenerated an output with any of these defects once and kept the better output; it was dropped, so every request whose output can be used costs exactly one call (with the retries of a transient failure, §7.9) and its latency is never doubled.
- **Output handling**: parse, check the schema and the narrative safety rules (missing localized or `*_en` fields are copied from their counterpart), and take the scenario from the classifier. An output that cannot be used at all (unparsable, or failing the safety check) is regenerated once, in the same request and under the same 35-second deadline, when the first call took under 15 seconds (`regenerateWithin` in `internal/controllers/ai/deadlines.go`), and the regenerated output is published if it passes. The interaction row then records both calls' tokens summed and the latency of both calls together. An output that is still unusable, or one the first call took too long to leave time for a second, is a 500 `failed to parse llm response` / `llm output security validation failed` (`MODEL_OUTPUT_INVALID`, §6.3); the rate limit charge is given back for an unparsable output and kept for one that failed validation (§7.1). The row's `model_output` is the regeneration's: it is cleared before the second call, so a second call that fails records none. This changes nothing for outputs with the minor defects above, which are published as they are: it costs about twice the tokens and latency on the failure path only.

### 7.9 Latency

The design keeps everything but the text independent of the model, and keeps the model call short and bounded:

- **The numbers do not wait for the endpoint.** The client computes the cards, the range and the chart corridor itself, so they render before the insight arrives (§8).
- **No model work for numbers.** Trends, ranked impacts, the scenario and the category counts are computed in code from the request; the main model only writes the text.
- **Rules before a model for pages.** Page classification (§5.8, §7.2) applies the rules first. A page they leave unresolved is looked up among the small model's verdicts on the site's pages from the last 7 days, which memcache shares across server instances. The small model is called only for pages without one, under a 4-second deadline, and a failure or timeout lets the request continue with the root rule only. On the real checkpoints the rules leave a single page unresolved (§5.8).
- **A short answer.** The main call runs with low thinking, and the response schema asks only for the scenario and three short texts (§7.6, §7.7), with the English intermediate fields only for locales that need a translation.
- **Bounded waits.** The main call makes up to three attempts under a 35-second deadline; its output is regenerated only when it cannot be used at all and the first call took under 15 seconds (§7.7). A transient failure (HTTP 408, 429, 500, 502, 503 or 504, or a dropped connection) is retried after half a second and then a second, each plus up to half a second of jitter (`mainGenerationRetry` in `internal/controllers/ai/deadlines.go`). Any other failure, a third failure, or running out of time is a 500 (§6.3); when the last failure is an error answer from Vertex AI rather than a timeout, the rate limit charge is given back (§7.1). The page classification is made once, since a retry would spend its 4 seconds. Waiting for a generation slot adds at most 1 second, and only on a full instance (§7.1). A synchronous request as a whole is bounded at 45 seconds, above the slot wait and the classification and model deadlines together, so it ends with its own error rather than being cut off (§7.1).
- **Warm instances.** App Engine starts new instances of the default service, which serves the endpoints, during scale-out, when traffic is high. A new instance gets ready in App Engine's warmup request (`/_ah/warmup`), before it serves traffic: it builds the services of every AI controller, the way their handlers do on their first request, then makes one `countTokens` call from each model client the endpoints use (`gemini-3.8-flash` and the classifier's `gemini-3.5-flash-lite`), all at once. Vertex AI does not bill `countTokens` and meters it under its own quota. The call fetches the Application Default Credentials token, which the client caches for about an hour, and opens the TLS connection to Vertex AI, which the first generation reuses if it starts within the connection's 90-second idle timeout. The warm-up runs once per instance and waits at most 10 seconds for Vertex AI. A step that fails is logged as a warning and left to the first request (`Warmup` in `internal/controllers/ai/warmup.go`; README, "AI Endpoints").
- **No repeated work.** A request identical to one answered in the last 24 hours returns the stored body before the rate limit, with no model call (§6.1). One identical to a request still generating makes no model call either: it joins that request's operation or gets a 409 with `Retry-After` (§7.1).
- **Asynchronous mode.** With `async: true` the endpoint returns an operation at once and generates in the background within 60 seconds, so the client does not hold an HTTP request open for the model (§6.2). Polling it is cheap: after the first poll, the same credentials are authorized from memcache for 5 minutes, and every response about a running operation says when to poll next (`Retry-After: 2`).
- **Payload last.** The request payload closes the prompt, so every request shares the request-independent instructions ahead of it (over 15,000 characters, `TestBenchmarkingPromptSharedPrefix`), which Vertex AI can cache to lower input cost (§7.10 on what that cache serves in practice). The per-request part before `<data>` (the scenario label, the locale glossary and language notes, the scenario example) varies with the locale, the scenario, the subject and shape, the period length, the range variant and `weeks_until_range`.

**Measuring.** `go run ./cmd/insights latency` runs the endpoint path concurrently on a seeded sample (by default 24 requests: half real-site checkpoints, built at `-period-days` days (28 by default), half golden-set entries at their own lengths) and times each stage: page classification, prompt build with the endpoint's options, the main call and output validation; the card computation runs untimed, as it is the client's. It prints p50, p75, p90, maximum and mean per stage and the token usage, leaving out one request reported as cold, and writes `output/latency/<timestamp>_<label>.json`. Flags: `-latency-n`, `-eval-seed`, `-timeout` (per request, 55 s by default), `-model`, `-thinking-level`, `-thinking-budget`, `-label` (`-label baseline` also writes `output/latency/baseline.json`) and `-compare <report.json>`, which prints paired ratios with 95% bootstrap intervals and a `WIN` / `REGRESSION` / `INCONCLUSIVE` verdict. Unlike the endpoint, the harness classifies pages with the main model, without the 4-second deadline and without remembered verdicts, and retries any failed model call, not only a transient one, for up to three attempts.

### 7.10 Cost and Token Efficiency

**Where the tokens go.** `go run ./cmd/insights count-tokens` counts every golden-set prompt with the Vertex AI CountTokens API and writes `output/cost/token_breakdown.json` (per-entry tokens, percentiles, the calibrated characters per token and the response-schema tokens). A localized request carries about 15k prompt tokens (about 13k of instructions, scenario example and glossary, and about 1.5k of payload after compaction) and returns about 250 output tokens (the English intermediate fields plus the localized ones; about 130 for English). The main call thinks at `LOW` and reports no thinking tokens. Output tokens are billed at several times the input rate (about 8× at Flash-tier list prices), but the prompt is about 60 times longer, so input is roughly 85–90% of a request's model cost.

**Implemented.**

- **Compact payload** (§7.6): compact JSON, positions rounded to one decimal and the card `excess` left out cut the payload from about 9.3k to 5.6k characters on the golden set (−40%, about 990 tokens per request) and the average prompt from 58.9k to 55.2k characters.
- **Telemetry** (`docs/ai_data_collection_and_quota_design.md`): every generated row records the main call's prompt, cached, output, thought and total tokens, and the page classifier's tokens and latency when the classifier's model was called (the rules and the remembered verdicts of §7.9 settle most pages without it); response-cache hits write a marker row; `ai_daily_aggregates` sums tokens per group and the statistics dashboard shows tokens per request, the cached share and the cache hit rate. Production cost and cache behaviour are read from these columns.

**What Vertex AI's implicit cache serves.** Measured with sequential requests on `gemini-3.8-flash` (`output/cost/latency/probe/`): the same prompt sent twice in a row reports about 12.2k cached tokens on the second call, but different requests sharing an identical instruction prefix of about 12k tokens, sent seconds apart, reported no cached tokens (9 of 9), and neither did the same prompt re-sent minutes later. The prompt layout therefore cannot rely on cross-request prefix caching for savings; the `cached_tokens` column is where production volume can show otherwise.

**Evaluated and not adopted** (each against a control built from the previous state, under the same judge and seed; numbers from `output/cost/results.md`; these runs predate the two-question contract of §1, so the seasonal slot and scenario names they mention no longer exist):

| Change | Saving | Why not adopted |
| :--- | :--- | :--- |
| Scenario- and locale-independent instructions (scenario and target locale moved after the instructions) | A cacheable prefix of about 12k tokens for every request of a language class, but no cache hits across requests (above), and +30 tokens for the per-request summary it needed | The model dropped the seasonal Slot 2 on flat-but-negative months (2/8 passes against 7/8) until a per-request summary restated the scenario and the Slot 2 phrase; with no cost or latency gain, the change was reverted. |
| Shorter examples (compact example JSON, `detailed_analysis` only when requested) | About 760 characters per prompt | Together with the per-request summary, an English seasonal entry fell to 2/13 against 4/5 on the control. |
| Direct localization (no `*_en` fields; localized fields written straight in the target language) | Localized output tokens −43% (about 248 → 143), localized p50 latency about −5% | Accuracy failures rose: over 200 entries × 2 runs it passed 393/400 (98.2%, 2 entries failing both runs; `POST_SURGE_PULLBACK` 59/64) against 399/400 (99.8%, none) for the control, all reasoning errors the English draft prevents (an `OFFSET` card's share described against the wrong direction, a `GROSS_CHANGE` share stated as a growth rate, the seasonal slot dropped). |
| Pruning settled rules, per-scenario rule blocks, de-duplicating field limits | Under 1% of the instructions; per-scenario blocks would shorten each prompt but split the instructions by scenario | Too small to measure against judge variance, and many rules are pinned by regression tests for failures they fixed. |

**Non-regression protocol.** Judge 200 golden entries with a fixed seed (`-eval-seed 20261022`) and the localization dimension (§10.4); build the control from the previous state and judge it under the same judge; re-run each failing entry 5–8 times on both prompts with the same judge (`output/cost/_rerun`) to separate flaky failures from regressions; bisect a regression across the steps that make up a candidate. Wall-clock latency is measured with sequential, interleaved requests (`output/cost/_probe`): concurrent waves of 24 timed out on most requests and do not compare prompts.

**Porting to Conversion.** Serialize its payload compactly (it still uses indented JSON), round its float metrics in the payload only, keep its English intermediate fields, and verify with the same protocol and the token columns.

### 10.1 One Code Path

The harnesses play the client and then call the same functions as the endpoint, including the model call: `evaluate`, `evaluate-sites` and the live period test generate through `BuiltPrompt.Generate`, so each output is one call with the bold repaired, as in production, and an output with a detectable defect is judged as it is (§7.7). `evaluate-sites` builds each checkpoint's request from the checked-in exports, classifies its pages (failing the checkpoint on error), computes the cards, renders the "Key Factors (UI Cards)" column from them, then builds the prompt (with `detailed_analysis` added for its Detailed Analysis column, and the `*_en` fields kept for English locales) and validates the output as the endpoint does; an output the endpoint would refuse is regenerated (at most 3 outputs). The Input JSON column is the sanitized request with its page verdicts and `decomposition`. `evaluate` classifies (failing open, like the endpoint) and computes the cards for each golden entry, and builds the prompt with the endpoint's options. `check-sites` re-verifies published CSVs without a model: it recomputes the cards from the Input JSON and fails rows whose recorded `decomposition` or card cell differs, along with unit, sub-row, required-card (`DIFFUSE` second `PRIMARY`, `OFFSETTING` and `≥25%` `NET_CHANGE` `OFFSET`), corrupted-bold, driver-phrasing and page-class rules.

### 10.2 Deterministic Replay of the Historical Sites

`internal/ai/real_corpus_replay_test.go` rebuilds every weekly checkpoint of the four checked-in sites in memory through the production path and compares scenarios and rendered cards against the two expectation CSVs (§5.10 *Parity*; regenerate with `-update-real-corpus` / `-update-classified-corpus`). Failures report how many checkpoints changed scenario before the per-row diff, and a row-count floor prevents a vacuous pass. Request building is deterministic (every sort breaks ties on the item's identity; positions are accumulated in date order), and a test requires byte-identical requests across rebuilds. Real payloads are never copied into the golden set.

### 10.2.1 Baseline Conformance

`internal/ai/baseline_conformance_test.go` checks the model of §5.4 and the `last_year` totals of §5.5 against the fixtures in `internal/ai/testdata/baseline_conformance/` (the PHP port's acceptance suite, at 7, 14, 28, 90 and 182 days); `internal/ai/real_corpus_replay_test.go` checks that cited real checkpoints (merch 2026-03-11..04-08, picoparker 2026-02-28..04-17, search_central 2026-02-09) carry a range and the status their out-of-sample band gives; and `TestCalculateRobustBaseline_CitedRealRows` (`internal/ai/baseline_model_test.go`) pins the range behaviour on the rows the v13 issue report cites: the four near-identical flips keep one status, picoparker 2026-04-03/10/17 and search_central 2026-02-09 read as within, and oi.ie's post-surge ranges (2026-03-06, 08-07, 08-28, 09-25) keep a lower bound of at least 40% of the midpoint and a relative half-width below 60%. The golden set's expected outputs use the range status phrases (§7.6); the judge grades against the Input Data's `status_vs_baseline` and the entry's own range wording variant (passed to the rubric), never the golden text's phrase.

### 10.3 Synthetic Corpus and Golden Set

- **Generator** (`internal/ai/synthetic/`): a round-robin walk of macro direction × range status (`ABOVE_EXPECTED`, `WITHIN_EXPECTED`, `BELOW_EXPECTED`, `NO_RANGE`) × scale tier × locale cells, so every label, including the status-against-direction ones (`ABOVE_EXPECTED.DOWN`, `BELOW_EXPECTED.UP`), is generated; the label is whatever the engine makes of the payload, never an input. Ranges are drawn with the half-widths measured on real sites (the profile's median and p90), placed so the total sits 0.5% (the "slightly" phrase; rounding can push the smallest sites to a figure), 3% (the 1–5% band quantified since the 5% floor was removed), 12% or 35% beyond the nearest bound. The end date (and with it the range wording variant, `RangeVariantFor`) and the distance advance once per round of range statuses, never with the status itself, so at the golden size every status meets every variant, with a figure and with "slightly" (`TestGenerateBenchmarkingScenarios_GoldenSizeCrossesEveryStatusWithEveryRangeVariant`). `NO_RANGE` entries carry `history_days` short of the history a range needs (from two periods when they are shorter than `MinRangeHistoryDays(d) = d + 28`, otherwise up to a period short of it, so 28–55 days at 28; a band needs `d + 55`), so their analyses state the check-back clause. **Period lengths:** the golden corpus walks the cycle 28, 7, 28, 14, 28, 90 days, shifted by one each round of cells so every cell meets every length (`benchmarkingPeriodMix`): half the entries at 28 days and a sixth each at 7, 14 and 90 (`TestGenerateBenchmarkingScenarios_MixesPeriodLengths`, `_EveryStatusMeetsEveryPeriod`). The totals, and with them every contextual figure, are scaled by `d / 28` (`scaleToPeriod`, rounded, at least 1), as the engine scales its count floors, so an entry built near a floor at 28 days sits near the scaled floor. `GenerateBenchmarkingScenariosForPeriod` builds a corpus at one length with the same scaling (the population evaluation's synthetic sites use it). Outside-range cells periodically carry a `last_year` that repeats the move (`_lastyear` suffix); others carry no context (`_nocontext`) or no Search Console data (`_nosearchconsole`). Entries are named by their factor tuple (`bm_down_above_micro_it-it_lastyear_2`). Payloads are built to the sizes measured on real sites from the same visit totals, and payloads with queries carry `search_clicks`.
- **Traffic profiles** (`internal/ai/synthetic/traffic_profiles.json`, regenerated with `go run ./cmd/insights extract-profiles`): distributions only (volume tiers keyed on the previous period, tier-conditioned volatility, direction × status joint frequencies, channel-mix categories, referrer archetypes, payload sizes, and the range's status mix, median and p90 half-width and last-year repeat rate); no site names, titles, queries or domains, which tests enforce on the file and the generated corpus. Real strings are used only for infrastructure the pipeline handles specially (search engines, AI assistants, social platforms, placeholders, dev and CDN hosts); other names are invented under `.example`.
- **Golden set** (`internal/ai/testdata/goldenset_benchmarking.json`): 449 entries: the 440 of the synthetic corpus, covering all 12 labels, every range status with and without the last-year clause, 20 entries for English and each of the 20 Tier 1 languages (`de-DE`, `es-ES`, `fr-FR`, `id-ID`, `it-IT`, `ja-JP`, `pt-BR`, `tr-TR`, `ko-KR`, `pl-PL`, `gl-ES`, `uk-UA`, `sr-RS`, `cs-CZ`, `ru-RU`, `vi-VN`, `nl-NL`, `ar`, `hu-HU`, `sv-SE`), and 20 entries total (weighted equivalent to a single Tier 1 glossary language) across a mix of 5 non-glossary Tier 2 scripts (`el`, `he_IL`, `hi_IN`, `th`, `zh_CN`, 4 each), storing expected outputs only plus a `corpus` block (`count`, `locales`, SHA-256 fingerprint). The 240 entries outside English and the first nine Tier 1 languages are clean-room references written by code (`buildCleanRoomGoldenEntry` in `internal/ai/eval/goldenset_locale_coverage_test.go`, regenerated with `-update-locale-goldenset`) by the current prompt rules: for a glossary language every analysis phrase, the driver's comparison, "led by" and "paid traffic" come from the same glossary data the prompt renders (`ai.LocalizedPhrasesFor`: the request's range variant, "slightly", the `NO_RANGE` phrase with its check-back clause, the last-year clauses) and the number separators from CLDR, so only the driver's verbs and connectors and the two subject sentences are written per locale; the Tier 2 scripts carry their own translations of the canonical phrases (variant A). A `CATEGORY` or `RECENT_CONTENT` subject is the analysis's second sentence and never in the driver, a `SEARCH_QUERY` keyword is the Organic Search card's `CONTEXT` row (dropped first when the driver would pass its limit), and the driver names an `OFFSET` card with `NET_CHANGE` ≥ 25 and the largest `PRIMARY` card's `DECOMPOSITION` sub-row ≥ 40. `TestBenchmarkingGoldenSet_CleanRoomEntriesFollowTheV13Rules` checks that every clean-room entry is what the builder writes, opens with its variant's status sentence, carries no retired wording ("remained stable", "multi-month", "than expected") and passes `OutputDefects` with no exemption; only the 200 legacy entries keep the "English driver does not name" exemption. In both synthetic scenario generation (`localeForScenarioIndex`) and stratified autorater sampling (`sampleBenchmarkingEntries`, whose strata are the 12 scenarios, the macro and status of each entry's name, so a sample of 12 or more covers every scenario; `applyLocaleOverride`), all non-glossary (Tier 2) locales share a single bucket weighted equal to one glossary-powered language. Loading regenerates the inputs and fails on a fingerprint mismatch when the generator changed (re-run `expand-goldenset`). Nine more are handcrafted cases written from abstract descriptions with invented names: six with non-Latin entity names (a Cyrillic article, an Arabic and a Devanagari category, Russian queries, Chinese articles, and a Japanese category in a Swedish site) and three with names that read as instructions to the model (an article title and search queries the prompt carries and the reference names verbatim, a category, and a `System:` referrer the input screens drop). They are corpus scenarios of clean-room locales with their names replaced, so their references are also `buildCleanRoomGoldenEntry`'s; each carries its request inline (`request`, `BenchmarkingGoldenEntry.Payload`) because no generator produces it, and `TestBenchmarkingGoldenSet_HandcraftedCases` (regenerated with `-update-handcrafted-goldenset`) checks that each is what `handcraftedCases` builds, passes `OutputDefects` and `LocalizationFailures`, and that an injection case's instruction-like name reaches the prompt and a non-Latin case's reference names its non-Latin name. `expand-goldenset` and `-update-locale-goldenset` keep them. Tests gate joint-state coverage, label reachability from complete payloads, and golden-set coverage.
- **Generation reliability**: golden-set generation runs in passes; failed entries are retried at lower concurrency, and only an entry failing both passes is fatal, with every casualty named. Terminal credential errors abort a run after one attempt.

### 10.4 Two Tiers

| Tier | Size | Judge | Asserts |
| :--- | :--- | :--- | :--- |
| A, deterministic (`internal/ai/synthetic/tier_a_test.go`) | 3,000 generated in memory | none; runs in `go test -short` | valid labels, card invariants, prompt buildability, the same verdict at every scale |
| B, judged (`evaluate`) | the golden set (`-eval-sample 200` by default), each entry `-repeat` times (default 3) | `gemini-3.8-flash`, high thinking | narrative quality, accuracy, tone, localization |

**Repeats.** Each (entry, run) is its own task on its own copy of the entry. The summary reports the overall pass rate, the first-run pass rate, a 95% bootstrap confidence interval over entries, and robust / flaky / systematic entries with the judge's reason; the command exits non-zero only when an entry fails every run. Failures are analysed from these passes, never by re-running single entries.

**Judge** (`internal/ai/eval/benchmarking_judge.go`, run by `EvaluateBenchmarking` in `autorater.go`): the rubric is split the way the insight is. The **range check** grades the analysis: it is exactly total + status phrase (the rubric is given the variant `RangeVariantFor(end_date)` selects as `AnalysisStatus`, with `range_distance_pct` as "about X%" when present, "slightly" with `range_distance_slight`, the check-back clause with `weeks_until_range`) + the last-year clause exactly when `repeat_last_year`, with no last-year claim the data cannot support. The **change check** grades the driver: it opens with the site's change matching `current_period_traffic` and `current_period_traffic_pct` ("the same as" with no figures for equal totals), never mentions the range, what is usual, normal, typical or expected, or last year, names the largest `PRIMARY` card, and keeps every card figure, share basis and keyword share on its own denominator. The two may point different ways and that is never a contradiction. Programmatically, the output's `scenario` must equal the engine's label exactly, and in English the last-year clause and seasonal claims are checked by regex (`LastYearFailures`). It receives the totals (`visits` without `last_year`), the computed trends with the entry's cards and the request without its `decomposition` or bounds, and judges only the user-facing `scenario`, `analysis` and `driver` (never the `*_en` fields), so it grades exactly what users read whichever way the prompt produced it.

**Localization.** The benchmarking judge scores a fifth dimension, `localization` (`genai.BenchmarkingScoreCardResponseSchema`; the conversion judge keeps the four shared ones): every user-facing field written entirely and fluently in the payload's locale with only names (channels, domains, titles, queries, campaigns, categories) left verbatim, no words borrowed from a third language, no CJK or Hangul in a Latin-script locale, the locale's number formatting with every figure unchanged, untranslated bolded channel and category names, and locale wording that keeps the rules' meaning (the visits word, the period never a month or a year-over-year comparison, the range status phrase preserving `status_vs_baseline`, never a movement verb or a month count). Programmatic checks (`LocalizationFailures`, `internal/ai/eval/localization.go`) back the verdict, all read from the language table (§7.6.1) and all on the field's own words, the bolded or quoted names left out, as are the request's campaign titles (`CampaignTitles`: CAMPAIGN cards, "Campaign" rows and paid members' top campaigns, matched verbatim in any case), which the Campaign Attribution Rule writes without bold or quotes: a field in a non-Latin-script language must contain its script (Cyrillic, Arabic, Greek, Han, Devanagari…), a Latin-script field must contain no other script, a non-Latin-script field no third script (Latin names and brands aside), a field with two or more distinct English marker words fails as untranslated English (markers that are words of the language, such as German "was" or Dutch "over", do not count), and a figure whose separators change its value for the locale's CLDR number format fails (`numberFormatFailures`: "13,000" in German, "1.234" in Japanese, "1,234.5" in Spanish; spacing variants pass). A non-Latin name kept verbatim in bold or quotes, such as a Japanese page title in a German driver, is no failure. The golden set's expected outputs pass every check (`TestLocalizationFailures_PassOnTheGoldenSet`). Replayed over 600 recorded outputs they flagged none, and they caught every English `*_en` text passed off as localized (180/180). A failed localization verdict fails the run even if the judge's `overall_pass` says otherwise. The summary breaks judged runs down by locale, with localization failures counted per locale, and by period length (`days_in_period`, with each length's flaky and systematic entries), and `-locale-override pt-PT,da-DK` re-targets the sampled entries at the given locales round robin (names suffixed `@<locale>`), so locales the golden set does not carry, or an all-localized stress run, can be judged. Rubric tests derive their expectations from generated payloads (every status and direction the classifier emits is named in the rubric, micro-scale figures are valid, partially populated contextual data is described).

**Length.** The autorater accepts each user-facing text up to its implementation limit (§7.6) plus 10%, rounded: in English analysis 275, driver 242 characters; in other locales (and for an entry without a locale, which gets the localized prompt) analysis 308, driver 253. A longer text fails `conciseness` and the entry's run, with the field, its length and the limit in the reason. The programmatic check and the judge rubric's conciseness line are both computed from the §7.6 constants (`toleratedBenchmarkingLimits`), so they cannot drift from the prompt. The `*_en` fields are not checked.

### 10.5 Threshold Boundary Pairs

The classifier and card thresholds are named constants, and `internal/ai/scenario_classifier_test.go` pins each one at its edge: the range bounds (inclusive, `TestDetermineStatusVsBaseline`), the 1% distance threshold below which the analysis says "slightly", on the exact ratio, and the half-up rounding above it (`TestRangeDistancePct`, `TestRangeDistancePct_AlwaysQuantifiedFromOnePercent`), the range wording variant rotation (`TestRangeVariantFor`), the weeks until a range (`TestWeeksUntilRange`), the last-year band-width boundary (`TestRepeatLastYear`), the subject order and materiality (`TestSubjectFor`), and that no rendered share exceeds 100% (`TestRenderedShareIsCapped`), so a retuned threshold moves its own tests.

### 10.6 Published Spreadsheets

`evaluate-sites` CSVs for oi.ie, shop.merch.google, picoparker.com and Search Central are published to the `Benchmarking Insights v13` tab of each site's tracking spreadsheet (v12 holds the previous contract's output); the tab holds the run on the daily-fit range of §5.4. The `Daily Visitors Trend` tab is the `export-chart-data` output (§5.6) for the same days, so its `Expected Range Min` / `Max` on a checkpoint's date are that row's request `baseline`, and the Dashboard's range chart plots its daily band. Columns: `Date`, `Standalone Link`, `Scenario`, `Key Factors (UI Cards)`, `Analysis`, `Primary Drivers`, `Detailed Analysis`, `Input JSON`. `Standalone Link` opens the row's site in the standalone Site Kit demo at the row's end date, through its frozen login form, which needs no session: `<base>/login/?mode=frozen&reference_date=<end date + 1 day>&site=<frozen id>`, since the demo reports on the days before its reference date. The demo opens in its own date range (28 days by default) and the link carries no period length, so it shows the row's period exactly for a 28-day run and the days up to the period's end otherwise. The base URL is the `-standalone-url` flag (default `https://standalone-dot-site-kit-dev.appspot.com`), which must be an absolute http(s) URL and is checked before the run starts, and the frozen ids are `oi_ie`, `merch`, `picoparker` and `search_central`. `check-sites` does not need the column, so CSVs written before it existed (the published v12 and v13 tabs) still check.

### 11.2 Checkpoints and Coverage

- Every series is cut to the range where GA4 and Search Console data overlap; checkpoints are weekly from `2d` days after its start.
- An export is used for a checkpoint only when its first and last dated rows bracket `[start of the previous period, T]`: a day without rows reads as zero, so a truncated export would otherwise turn into a fake decline. Without coverage the breakdown is left out (the cards then carry no row from it). The Search Console exports are gated the same way. This gate belongs to the client: the endpoint receives totals only and cannot tell a missing day from a zero day.

### 11.3 Extraction Scripts (`internal/ai/testdata/scripts/`)

- **`fetch_ga4.py`**: pulls the GA4 exports above (except `channel_campaigns.csv`, which it does not produce) and the conversion exports through the Data API with full pagination; `--reports` limits the run; `--dates_from <csv>` reuses an export's date span. Long-tailed exports are trimmed to keys that rank within a fixed depth in any rolling 28-day window (`pages` top 60 by visits, `referrers` top 40 by `|Δ|`, `channel_pages` top 30 per channel and direction), always keeping root and placeholder rows, the first and last day and WordPress posts; every checkpoint gives the same request and cards on trimmed and untrimmed exports. `--no_trim` and `--trim_only --output_dir <dir>` control trimming.
- **`fetch_sc.py`** (tests: `fetch_sc_test.py`): reads `wmx_processing.SearchDataV2_SiteImpression` with `f1-sql readonly` (accounting group `site-kit-service-prod`), one property per site (overlapping properties double-count), one query per calendar month, finalised partitions only, never a partial day; writes `sc_queries.csv` (top 140 queries per day by clicks, then impressions) and `search_console.csv`.
  - **One run per day.** The day and the output run come from the run name in `_PARTITION_NAME` (`.../SearchDataCanonical/2026-08-14T19-00-01Z/...`). Only the latest run of each (day, property) is read, for both tables, so a day's totals and queries come from the same run. Each fetch prints, per site, how many days had more than one run and which. A (day, property, table) still holding more than one run, two tables from different runs, or a kept run that is not the latest stops the fetch before anything is written.
  - **Merge by date.** Fetched days replace their rows on disk and every other day on disk is kept, so a fetch never shrinks the files. A day the result has no rows for keeps its local rows, and the site and day are printed. A `search_console.csv` row is replaced only by a fetched totals row; a fetched day with totals and no queries replaces that day's `sc_queries.csv` rows with none.
  - **Options.** `--incremental` resumes from the newest day on disk. Without it a fetch starts at `--start_date`, by default 2025-06-04 (`DEFAULT_START_DATE`, the oldest day F1 served on 2026-10-21). F1 skips missing days inside a range and fails a range that holds no partition at all; such a month (expired, or not written yet, e.g. a new month on an `--incremental` run) is printed and skipped, and its local rows are kept. `--dates=YYYY-MM-DD,...` refetches just those days, one query per day; a day F1 no longer has (or whose queries have not landed) is printed and left as it is on disk.
- **`fetch_wp_posts.py`**: downloads every post of a WordPress site through its REST API (`/wp-json/wp/v2/posts`) into `posts.json`.
- **`update_all_testdata.py`** (tests: `update_all_testdata_test.py`): incremental GA4 and Search Console updates for every site in one command; `--full_refresh` runs `fetch_sc.py` without `--incremental`, so the Search Console refresh starts at its `DEFAULT_START_DATE`.
